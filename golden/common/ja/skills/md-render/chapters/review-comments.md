# レビューコメントと見出し（セクションアンカー・コメント・対応済みバッジ・Atomic）

> この章を開く作業: レビューコメントに応える時。見出しを付ける時。コメント欄の挙動を決める時

## セクションアンカー（sha1・全報告書）

見出し id は `sec-<sha1(正規化見出し)[:8]>`（位置非依存・見出し依存）。再レンダリングしても見出しが同じなら id 不変 → アンカー付きコメントが迷子にならない。TOC・要判断リンクは同じ id 由来で自動整合。同一テキストの H2 は id を共有（`--lint` が警告）→ コメント合流を避けるため見出しは一意にする。

## コメント機能 & 返信プロンプト（報告書・既定 on）

報告書（`isReport` 判定: frontmatter `doc_id`/`report_id`/`audience`/`status` か、本物の見出し（H2〜H4。コードブロックの中は数えない）の「本報告書の読者と目的」）で**安定 id（`report_id` か `doc_id`）がある**場合、各本文 H2 直下にトピック別コメント Composer と返信プロンプト生成を付与する。`comments: off` で抑止。

- **localStorage のみ**（キー `ccpit-cmt:<reportId>:<sectionId>`）。コメントは HTML 本体に焼き込まない → 決定論（`同一MD→byte一致`）と `HTML⊆MD`/`MD⊆HTML` を維持（Composer は空コンテナ + CSS/aria ラベル + 空 textarea ＝静的テキストノードゼロ。on/off の `extractTextNodes` 一致テストで検証）。
- **reportId は MD 由来のみ**（`report_id`/`doc_id`）。ファイル名 fallback なし（ファイル名は MD 外で byte 一致を壊す）。id 不在ならコメント無効。
- **返信プロンプト** = 全コメントの固定整形集約（LLM 不使用）→ `navigator.clipboard.writeText` ワンクリックコピー（`file://` 等の非 secure context は `execCommand('copy')`+select にフォールバック）。返信本文生成（レビュー担当 / CC）は本レンダラの責務外（層分離）。
- コメント報告書にのみ注入。非コメント文書は byte 不変。


## コメント対応済みバッジ（任意・`comments_resolved:` ブロック）

frontmatter に `comments_resolved:` ブロックで `- 見出し || 対応メモ`（2部）または `- 見出し || 元コメント || CC対応メモ`（3部）を列挙すると、該当見出しのコメント欄に「✓ 対応済み」バッジ＋対応メモを表示する。**レビュアーの localStorage コメントとは別レイヤ**で、CC（対応した側）が解決状況を HTML に焼き付ける層。

- **3部（元コメント埋込・読取専用）**：3部宣言時、レビュアーの元コメントを**読取専用で埋込**（編集UI無し・`< > & " '`/`</script>` エスケープ済データ島＋`textContent`＝改変不可）。表示順 [元コメント読取専用]→[✓対応済み＋対応メモ]→[再コメント]。見出し不一致の元コメント/メモはデータ島に入れない（情報露出防止）。
- **コピー除外**：resolvedMode 時は返信プロンプト集約を `REPLY_GEN_RESOLVED`/`REPLY_GEN_ATOMIC_RESOLVED` に差替え、**対応済み見出しの localStorage コメントを集約から除外**（過去コメントの冗長コピー防止）。非resolved文書は既存ローダを byte 不変で使う。
- **再コメント欄**：対応済み見出しに別キー `<id>:re` の編集 Composer を出す（集約コピー対象＝新規コメントは拾われる）。元の基底Composerは読取専用埋込に置換（確定コメントは編集不可）。
- **2 巡目以降の対応済み化（2026-09-13）**：再コメント欄（`<id>:re`）に書かれたコメントは、key に `:re` を後置した宣言 `- 見出し:re || 元コメント || メモ` で同様に対応済み化する（n 巡目は `:re` を n−1 個）。3 部なら `<id>:re` が読取専用埋込＋✓＋メモになり、次層 `<id>:re:re` の再コメント欄が出る。2 部ならその再コメント欄の末尾にバッジ＋メモを添える。`:re` 層は 1 つ浅い層が 3 部で宣言されている時だけ描画（無ければ lint 警告）。除外集合にも `<id>:re` が入り返信集約から外れる。`:re` 宣言の無い文書は byte 不変。**前巡の宣言に合成してはいけない**（再コメント欄が未処理のまま残り、集約にも毎回乗る）。

- `resolvedMode = commentsMode && fm.comments_resolved.length`（**report_id によるコメント機能が前提**）。宣言時のみ CSS/JS/データ島を注入し、非宣言文書は byte 不変。
- 見出し一致は `sec-<sha1(canon(見出し))[:8]>` で照合。バッジ「✓ 対応済み」は CSS 擬似要素（`<style>`＝`extractTextNodes` 除外）。対応メモは `<script type="application/json" class="mdr-resolved-data">` データ島から `textContent` で注入（`innerHTML` 不使用・実行時 fetch なし・`</script>`/特殊文字エスケープ）。
- **見出しに一致しない/重複 key の対応メモはデータ島に入れない**（画面非表示でも HTML ソースに残る情報露出を防止）。不一致 key・壊れた行・前提不成立は lint 警告。
- **key に使える見出し＝Composer が付く見出し**：本文 H2（atomic 時は H3 も）に加え、**Composer 付きパネル 3 種（`本報告書の読者と目的`／`結論の概要`／`スコープ外提案（Pending）`）の H2 も可**（2026-09-06 修正。従来は本文 H2 のみが島に通り、`結論の概要` への返信が lint 無警告のまま黙って落ちていた——lint は全見出し照合・render は bodySecs 照合という乖離が原因。`renderableIds` にパネル 3 種を追加して整合）。要判断一覧パネルは見出し由来 id を持たないため key にできない。
- 用途：レビューコメント → CC 対応 → frontmatter で `comments_resolved` 宣言 → 再生成で「✓ 対応済み」表示。レビュー往復の取りこぼし防止。

## Atomic コメント（任意・`comments: atomic`）

`comments: atomic` を宣言すると、H2 末の総括 Composer に加え、**各 H3 小見出しのサブセクション直下にもコメント Composer** を出す（H2＋H3 の二層）。トピック（例 §11.2）の直下でコメントでき、大節を読み切って末尾までスクロールする認知負荷を避ける。

- `atomicComments = commentsMode && fm.comments === 'atomic'`。**`comments: on`/既定/`off` は従来通り H2 のみ**＝既存文書 byte 不変（H3/H4 を含む `comments: on` 文書も live と byte 一致）。
- H3 Composer はテキストノード非生成（既存 Composer と同型）＝決定論・`HTML⊆MD` 維持。`comments_resolved` の対応済みバッジも atomic 時は H3 見出しに付けられる（同じ欄で Composer と共存＝再コメント可）。
- 返信プロンプト集約は H3 コメントを正しい H3 見出し・本文範囲で拾う。同名 H3 は id 衝突するため atomic 文書で lint 警告（見出しを一意に）。
- **推奨**：レビュー往復が多い報告書・議事録は `comments: atomic` を既定にする（トピック単位コメント）。

## 手順書のチェック欄（任意・`checkboxes: on`）

> この節を開く作業: 人が 1 手ずつ実行して結果を残す手順書（再起動・設定変更・試験の合図など）を書く時

**手順書の形**: コメント欄が文書の下部にまとまっていると、手ごとの結果を書きづらい。OK だった手は印を付けるだけで済ませ、記入の負荷を下げる。

- frontmatter に `comments: atomic` と `checkboxes: on` を宣言する。
- 手ごとに H3（`### 手 N: …`）を切る。`comments: atomic` により **コメント欄が各手の直下**に出る。
- 各手の末尾に **チェック欄**を置く: リスト項目の先頭を `[ ] `（未）か `[x] `（済）にする。例 `- [ ] 手 1 OK（期待値の 1 行が出た）`。事前確認のように 1 つの手に複数置いてもよい。
- 躓いた点・貼り付けたい出力だけをコメント欄に書く。
- 手順書の中身の規律（1 ステップ 1 動作・合格条件・返信書式）が要る場面では、それを定める skill（人間オペレータ向けの走行前手順書など）に従い、本節は描画の部品として併用する。

レンダラの挙動:

- **`checkboxes: on` を宣言した文書だけ**が対象。宣言の無い文書の `- [ ] 文` は従来どおり文字のまま出る（既存の受け入れ条件リスト等が再生成で黙って変わらない）。
- 宣言した文書では、`[ ]`/`[x]`/`[X]` の印を本文から外して `<input type="checkbox">` にする（印はテキストノードにならず、`--verify` も同じ規則で片を切る＝`HTML⊆MD`・`MD⊆HTML` とも通る）。初期状態は MD の `[x]`。`- [ ]` だけで本文が無い行はチェック欄にせず、文字のまま出す。
- クリックした状態は **localStorage**（キー `ccpit-chk:<report_id>:<通し番号>:<文の先頭 40 字>`）に保存し、HTML 本体は変えない。同じ PC・同じブラウザで開き直せば残る。キーの id は専用属性 `data-task-id` で渡すので、`comments: off` の文書でも保存される。`report_id`/`doc_id` が無い文書は保存しない（その場限り）。
- 済みの項目は取り消し線＋薄色。本文の上に「チェック n / 全数」の進捗が出る（擬似要素＝静的テキストを増やさない）。
- CSS/ローダはチェック欄を 1 つでも描いた文書にだけ注入する。宣言しても該当項目が無ければ注入しない。
- MD を書き換えて再生成すると、通し番号か先頭 40 字が変わった項目のチェックは引き継がれない（文面を変えていない項目は残る）。
- **`--lint` が発火の失敗を警告する**（非ブロック・`exit 0`）: `checkboxes:` の値が `on` 以外（`yes`・`true`・タイプミス）なら「未知の checkboxes 値」、`on` を宣言したのに有効な項目（`- [ ] 文` / `- [x] 文`）が 1 件も無ければ「有効なチェック項目が 1 件も無い」を出す。どちらも `[ ]` が文字のまま残る状態なので、生成後に `--lint` の警告を読む。
