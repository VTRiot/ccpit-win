# 図の塗りと文字色の対

> この章を開く作業: 図に色（`fill`）を付ける時。配色を明示した MD を HTML にする前

## 図の塗りと文字色の対

レンダラは mermaid を **dark テーマ固定**で初期化する。dark テーマのノード文字色は既定で明色系が入る（mermaid はノード文字色を primaryTextColor に従わせ、darkMode ではその既定値が明色になる）。したがって **`fill` に明るい色だけを与えると、明背景に明文字が乗り判読不能になる**。既定の文字色は「暗い塗りが来る」前提で決まっており、明るい塗りを置いた時点でその前提は成立しない。

- mermaid の `style` / `classDef` で `fill`（塗り）を明示したら、**同じ宣言で `color`（文字色）も明示する**（推奨される書き方）。テーマ既定の文字色に委ねない
- 配色は diagram-craft の `templates/palette.md` に従う。**パレット外の色は使わない**（diagram-craft の禁則。本 skill はここに例外を作らない）。別の色が要るならまず diagram-craft 側でパレットを拡張する
- コントラストの水準は WCAG 相対輝度比で見る（通常テキストの AA 基準は 4.5:1、大きな文字は 3:1）。**本検査は文字サイズを判定しないため、常に通常文字の基準 4.5:1 を一律に要求する**。大きな文字向けの緩和（3:1）は本検査の対象外（過検出の余地はあるが見逃しよりは安全側）
- **対を書いただけでは可読性は保証されない**。`fill` と `color` に同系色を置けば、対は揃っていても読めない。保証が及ぶのは「不透明な塗りと文字色の組で、比を実測して基準を満たした宣言」に限る。`opacity` / `fill-opacity` / `stroke-opacity` はそれぞれ独立したプロパティとして図全体で最後に設定された値を見る（途中で 1 未満にしても最終的に 1（100%）へ戻せば taint は解除される。逆に一度も明示しなくても途中の宣言で 1 未満にしたまま図が終われば taint になる）。値を解釈できない場合（変数・関数記法など）も安全側で taint（判定不能）とする
- **同一ノード / クラスへの複数回の宣言は、その図（mermaid フェンス 1 つ）内で合成した最終状態で判定する**。「1 行目で `fill`、2 行目で `color`」のように分けて書いても、最終的に対が揃い基準を満たせば合格する。逆に、後続の宣言が `color` だけを上書きして対が崩れた場合も検出する（`fill` を再宣言していない上書きだからといって検査対象から外れない）。ノード ID / クラス名は**図（フェンス）ごとにスコープが閉じており**、別の図で同じ名前を使い回しても混線しない
- `classDef a,b,c fill:...` のように**複数対象を一括定義する宣言**は、対象ごとに独立した鍵として合成する。一括定義した対象の一部だけを後続の宣言で個別に上書きしても、その対象だけの最終状態として正しく検出する
- **クラスの適用（`nodeId:::className` や `class nodeId className`）は解決しない**。`classDef` と、それが適用されるノードの直接 `style` は別々の鍵として評価する。クラス側に `fill`、適用先ノードの直接指定に `color` だけがある（またはその逆の）組み合わせは、本検査では対が揃っているとは判定できず、`PAIR_MISSING` になるか、あるいは見かけ上は無関係な宣言として素通りする。この組み合わせを使う場合は目視で確認する（クラス適用の解決は本提案の対象外とする — スコープを広げるほど mermaid のカスケード規則の再実装に近づくため、意図的に対象外とした）
- `fill` / `color` / `opacity` 系の値に **`!important`** が付いている場合、CSS と同様に非 `!important` の宣言より優先する（`!important` 同士は後勝ち）。これを無視すると、先に `!important` で下げた不透明度を、後続の通常宣言が誤って解除したものとして扱ってしまう
- **終了値 `0` は、本検査が解決する範囲（`style`/`classDef` 宣言に直接書かれた対とその実効値）に違反が無いことだけを意味する**。クラス適用を経由した合成（前項）は対象外であり、描画結果の実際のコントラストを保証するものではない。目視確認（次項の手順 4）は省略可能な追加確認ではなく必須の補完手段である
- **SVG フェンスはこの規則の対象外**。SVG では文字色も `fill` で与えられ `color` ではないため、同じ検査を当てられない。SVG は描画結果の文字と背景を目視で確認する

### 生成前の検査（成果物の合格条件）

図に配色を明示した MD を HTML 化する時は、**HTML を生成する前**に次を回す:

1. 対象 MD を検査する（スクリプトは `chapters/figure-colors-script.md`）
2. 終了値 `1` なら宣言を修正し、**終了値 `0` になるまで再検査**する。`0` になるまで HTML を生成しない
3. 終了値 `2` は「違反なし」ではない。原因を解消して再実行する
4. HTML 生成後、当該図を開いて文字が読めることを目視で確認する（本検査は宣言の検査であって描画の検査ではない）
5. この検査による生成保留は「HTML を作ると決めた時点で同ターンに出す」（出力要件）の**例外**である。検査失敗時は「未生成＋違反箇所」を同ターンで報告すればよく、判読不能な図のまま無理に生成しない。「レンダラ不在環境では省略してよい」（使い方節の fail-soft）とは独立の話で、両者は別軸で効く

検査本体のスクリプトは `chapters/figure-colors-script.md` にある（`figure-contrast-check.cjs` として保存して使う）。

```bash
node <保存先>/figure-contrast-check.cjs <走査ルート>   # 省略時 "."
```

- 終了値: `0` 違反なし / `1` 違反あり / `2` 検査失敗。**出力が空であることを合格の根拠にしない**（読取失敗でも標準出力は空になり得る）
- 検出種別は 4 つ。`PAIR_MISSING`（`fill` の合成があるが `color` が無い）/ `LOW_CONTRAST`（比が基準未満）/ `DUP_PROP`（同一宣言内で同じプロパティが重複。後勝ち規則に依存させない）/ `UNDECIDABLE`（**値全体**が色形式に一致せず比を出せない、または `opacity`/`fill-opacity`/`stroke-opacity` の最終値が 1（100%）未満、もしくは解釈できない値で実効コントラストを実測できない。変数・関数記法・8 桁透過・未知の色名・不透明度低下のいずれもここに入る。解決する色名は `white` / `black` のみ）。`UNDECIDABLE` は保留ではなく違反として扱い、実測できる指定に直す
- `opacity` 系プロパティは fill/color とは独立に、図（フェンス）全体を通じて**最後に設定された値**（`!important` がある場合はそれを優先）で判定する。途中で 1 未満にしても最後に 1（100%）へ戻せば taint は解除され、逆に最後を 1 未満のまま終えれば taint になる。`.5` のような先頭 0 省略・`50%` の百分率表記も解釈する
- **`!important` は CSS と同様に優先する**。`fill`/`color`/`opacity` 系のいずれについても、`!important` 付きの値は非 `!important` の後続宣言に上書きされない（`!important` 同士は後勝ち）
- `classDef a,b,c fill:...` の**複数対象一括定義**は対象ごとに独立した鍵で合成する。一部の対象だけを後続の宣言で個別に上書きした場合も、その対象の最終状態として正しく判定する
- **クラス適用（`:::className` / `class nodeId className`）は解決しない**。`classDef` 側の宣言と、適用先ノードの直接 `style` 宣言は別々の鍵として評価する。両者にまたがって初めて対が揃う設計は本検査の対象外（意図的なスコープ限定）。この組み合わせは目視で確認する。**終了値 `0` は解決範囲内で違反が無いことだけを意味し、クラス適用を含めた描画結果のコントラストを保証しない**
- 値は**部分一致で合格させない**。`color:#111-invalid` は `#111` として読まず `UNDECIDABLE` にする
- 判定は **mermaid フェンス内に限定**し、行を宣言単位に割ってから見る。分割は `;` のトップレベル出現のみで行い、`"..."` や `[...]`/`(...)`/`{...}` の内側（ノードラベル等）の `;` では割らない — ラベル本文に `;` と `style ... fill:` 相当の文字列が偶然含まれていても宣言として誤認しない。地の文や `bash` フェンス内の説明用コードも拾わない
- フェンスは開始と終了を分けて判定する。終了と認めるのは**同種・同長以上で、マーカー以降が行末まで空白のみ**の行に限る（レンダラの終了判定 `md2html.cjs:286` と同じ規則）。外側フェンスが mermaid でなければ内側は一切走査しない — 説明用に掲載した mermaid 例で検査を止めないため
- mermaid の**コメント行（行頭 `%%`）は宣言として扱わない**。コメント中に書いた説明用の `style` 例で終了値を `1` にしないため。mermaid のコメントは行単位の仕様なので、行途中の `%%` はコメントと見なさない（その場合は値が色形式に一致せず `UNDECIDABLE` になる）
- プロパティの記述順は問わない（`stroke` が `fill` より前にあっても検出する）
- 除外ディレクトリは `node_modules` / `.git` のみ。一部ディレクトリだけを見て全体の不在を主張しない。`.md` の拡張子判定は大小文字を区別しない（`.MD` も対象）
- ディレクトリのシンボリックリンクは辿らない（循環参照によるハングを避けるため）。配下を含めたい場合は実体パスを直接指定する
- **判定は図（mermaid フェンス）単位で、同一図内の `style` / `classDef` 宣言を合成した最終状態を見る**。「`fill` だけの宣言」と「`color` だけの宣言」が同じノード/クラス名で複数回に分かれていても、最終的に対が揃えば合格し、後から `color` だけを上書きして対が崩れれば検出する。ノード ID / クラス名のスコープは図ごとに閉じるため、別の図で同名を使い回しても混線しない

### リポジトリ全域の棚卸し（成果物検査と分ける）

走査ルートをリポジトリルートに向ければ全域棚卸しになる。**棚卸しの結果は、今生成している成果物の合格条件ではない**。無関係な既存文書の未修正箇所まで毎回の作業範囲に取り込むと、作業が際限なく広がる。全域で出た箇所は別件として記録し、その文書を次に触る時に是正する。
