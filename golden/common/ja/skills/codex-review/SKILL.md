# codex-review — 独立 Codex 第二レビュアー（汎用）

## 0. このスキルの役割

成果物や判断に対し **Codex の独立した第二意見**を助言として得る。最終権限は持たない。最終ゲートは常に人間。本スキルは Skill 機構経由で発火するため、Codex companion を Bash 直接呼びする場合と違い、活動が発火統計／フィードバックループに乗る。

`marshal-review` を補完する、軽量な隙間埋めの層である。`marshal-review` は実装変更（rule/code/bundle）があるたびに **git working tree に対する Codex adversarial-review** を回す強制ゲート。本スキルはその強制ゲートが届かない領域を担う。

## 0-A. `codex-cli-crossref` skillとの切り分け（先に確認）

本skillが呼ぶ実体は**プラグイン同梱の`codex-companion.mjs`**（`task`サブコマンド、`--prompt-file`引数対応）であり、これは実装前の設計文書・Skill候補・その他working-tree差分でない成果物という**（コード差分自体は含まない）成果物のレビュー**を担う（実際のコード差分は§2にある通り`marshal-review`の`adversarial-review`の役目であり、本skillはそれと重複しないよう調停する）。

これに対し、**事実調査・研究結論を独立エンジンで裏取りしたい**（コード差分でも設計文書でもない、事実主張のクロスチェック）場合は、本skillではなく`codex-cli-crossref`skillを使う。`codex-cli-crossref`は**グローバルインストールされた生の`codex exec` CLI**を直接呼ぶ別ツールの手順であり、プロンプトの渡し方（stdinリダイレクト。`--prompt-file`フラグは`codex exec`には存在しない）・記録先（呼び出し元の報告書に直接引用。CCPITレビューボックスへは記録しない）が本skillと異なる。

判断に迷ったら次の1問で切り分ける: 「対象は事実調査・研究結論の独立クロスチェックか？」→ Yesなら`codex-cli-crossref`、それ以外（実装前の設計文書・Skill候補のレビュー、および§1(c)のその他working-tree差分でない成果物のレビュー全般。実際のコード差分そのものは引き続き`marshal-review`）なら本skill。**§1(c)の対象は本節で除外されない**——本節が切り出すのは「事実調査クロスチェック」という具体的な1用途のみであり、それ以外の非コード差分成果物レビュー全般は引き続き本skillの領分である。

`codex-cli-crossref`skillが未採用/未配備の環境では、`~/.claude/skills/codex-cli-crossref/`は存在しない。その場合は本節の誘導先が無いものとして扱い、事実調査クロスチェックであっても人間レビューへ縮退する（§4の縮退方針に準じる）か、公式の非対話モード手順（`codex exec`の直接呼び出し）を都度確認しながら暫定的に使う。

## 1. 発火条件 — と marshal-review との調停

独立した Codex 第二意見が価値を生み、**かつ** `marshal-review` が同一タスクをカバーしていない時に発火する。典型的な文脈:

- (a) **計画/設計レビュー** — 実装着手*前*に plan / design 文書を pressure-test する（コード変更がまだ無いので `marshal-review` は発火しない）。
- (b) **Skill 採用候補レビュー** — 候補の提案 SKILL.md 内容（working-tree 差分でないテキスト成果物）をレビューし、結果を CCPIT のレビューボックスに記録する（§3-A）。
- (c) その他、独立レビューに値すると判断した、working-tree 差分でない成果物。

**調停（二重実行をするな）:** 現タスクで `marshal-review` が発火する／発火すると既に分かっている（= 実装変更がある: rule / code / 報告書 bundle）場合、**取り下げる**: 本スキルを回さない。その場合は `marshal-review` が既に独立 Codex レビューを提供しており、両方回すのは冗長な二重 Codex 実行になる。取り下げ判断は報告書／会話に明示せよ。沈黙スキップ禁止。`marshal-review` がカバーするか迷う時は、強制ゲートである `marshal-review` を優先し本スキルを退かせる。

候補レビューが衝突しない理由: 候補は*提案*段階（まだ skill ファイルを編集していない）なので `marshal-review` は発火しない。実際の skill 変更は後段の*採用*時（CCPIT の認証付き apply）で起き、そこで `marshal-review` が発火しうる — 経路が分離しているため二重実行にならない。

**コスト二段（コスト関門）:** 候補レビューでは、一次フィルタを通過した候補 — `adoption_label: recommend` かつ `review_verdict: pending` — のみ Codex を呼ぶ。レビュー済み・reject ラベルの候補に Codex を使うな。

## 2. Codex 呼び出し（安定形必須 — 実行時判断は companion パス解決のみ）

Codex companion スクリプトのパスはバージョンで変動するため動的に解決する（`marshal-review` と同イディオム）:

```
~/.claude/plugins/cache/**/codex-companion.mjs
```

- 1 件ヒット: それを採用。
- 複数ヒット: **semver 最大**を採用（例: `1.0.4` と `1.0.5` なら後者）。旧バージョン残置事故を防ぐ。
- 0 件ヒット: Codex プラグイン未配備とみなし、人間レビューへ縮退（§4）。

Bash で直接呼ぶ（disable-model-invocation 回避の既知手）。read-only（`--write` なし）:

```
node "<解決した codex-companion.mjs>" task --cwd "<実在する絶対パス>" --prompt-file "<レビュープロンプトの絶対パス>"
```

本スキルは **提供されたテキスト成果物**（plan / design 文書、または候補の §1-§3 SKILL.md）をレビューするため `task` サブコマンドを使う。git working-tree 差分のケースは `marshal-review` の `adversarial-review` の役目。レビュープロンプト（成果物テキストを含む）はファイルに書き出し `--prompt-file` で渡し、verdict + findings を返すよう Codex に求める。

レビュー観点はドライに具体的に:

- 候補レビュー: *本質的な UX 向上か。類似する既存 skill と統一可能か。*
- 計画/設計レビュー: *隠れた仮定は。検討されていない代替案は。要件カバレッジ／副作用は。*

## 3. findings の記録

### 3-A. 候補レビュー → CCPIT レビューボックス

Codex stdout を `verdict`（`approve` / `needs-attention`）と `findings` に整理し、**記録スクリプト（正規経路）**で CCPIT のレビューストアへ記録する。**提案 MD は書き換えない**（この節が指すのは §5 レビューボックスの自動転記手順の話——CC が §5 を手書きで上書きしない、の意。候補本文の改稿は §3-A-1 が定める別の活動であり、そちらは改稿の主体が異なる）。CCPIT が list 時に `request_id` をキーに本ストアをレビューボックスへマージする。

ストア: `~/.ccpit/proposal-reviews.json` — **直接編集（手書き upsert）禁止**。読み側ゲートと同じ述語で書込前検査する記録スクリプトだけが書く（手書きは「書けたのにゲートで落ちる」記録や型不一致を作る）:

```
node ~/.claude/scripts/proposal-review-record.cjs --request-id <id> --batch-file <batch.json>
```

batch JSON（骨子）:

```json
{
  "verdict": "approve | needs-attention",
  "findings": "<[n] 連番のレビュー本文。読者の言語（既定: 日本語）で書く>",
  "findingsOriginal": "<レビュアが別言語で返した場合のみ、原文をそのまま（任意）>",
  "reviewerId": "codex",
  "ccRebuttal": "<findings への反論／応答があれば（任意）>",
  "reviewRounds": 1,
  "adjudications": [{ "id": "1", "decision": "rejected", "reason": "<実質的な理由>" }]
}
```

- `reviewedAt` / `proposal_hash` / `adjudicationsFor` は**渡せない**（スクリプトが記録実時刻・提案 MD 実測・findings 本文から計算する — 推定／丸め・転記ズレの混入余地を消すため）。
- `adjudications[].id` は**文字列**（`"1"`）。JSON 数値で書くと拒否される（読み側ゲートが `[n]` と型込みで照合するため）。
- findings に `[n]` 指摘がある場合、**全件の終端裁定（`rejected`/`deferred`）が揃うまで記録できない**。裁定途中の中間状態は記録せず、刈り取りループ（改稿→再レビュー or 裁定）を完走した最終ラウンドを記録する。**指摘が 0 件（`VERDICT: approve` かつ指摘なし）の場合は `findings` に `FINDINGS: none` を含め、判定可能な形で明記する**（記録スクリプトはこの文字列と `verdict: approve` の組を刈り取り完了として扱う）。
- スクリプト不在の環境では手書きで代行しない。レビュー結果を作業ログに残し、スクリプトの配備を人間へ求める（レビュア不在の縮退は §4）。
- findings と自分の反論（§4）の両方を記録する。採用／却下の最終判断は人間が CCPIT のパスワードゲートで行う。

### 3-A-1. 候補が実行可能スクリプトを埋め込む場合の追加検証

**担当の分離**: 本節の抽出・実行・改稿は**呼び出し元 CC が行う**（§2 の Codex 呼び出しは read-only のレビュー意見取得のみで、コードの実行や候補の改稿は Codex の役目ではない）。候補本文の改稿主体は既存の統治規範（提案 MD を改稿するのは CC）に従う。

候補の完成版（提案 MD の「## 3. 変更後の完成版」ブロック）が Node.js 等の実行可能スクリプトを含む場合、**Codex の静的レビューだけで「指摘に対応した」と結論しない**。指摘の刈り取りループ（改稿→再レビュー、§3-A の「全件の終端裁定が揃うまで記録できない」の各改稿サイクル）ごとに次を行う:

1. **抽出**: 候補本文のコードブロックから**そのまま抜き出して**、作業用の一時ディレクトリ（プロジェクトの working tree の外）へファイル化する（手で打ち直さない）。**外部への書き込み・実データ・資格情報を要するコードは実行しない**——隔離した一時領域とダミー入力（フィクスチャ）だけを対象にする。ランタイム・依存関係が用意できず実行できない場合は「未検証」と明記し、「検証済み」を名乗らない（この場合、当該指摘は §3-A の刈り取りで `deferred` の対象になりうる）。
2. **反例の実測（実行結果を伴う指摘のみ）**: Codex の finding のうち、**コードの挙動に関する指摘**（実行結果が変わる類）については、不具合を再現する MD フィクスチャ（またはそれに相当する入力）を作り、**修正前のスクリプトで実際に実行して失敗することを確認する**（反例が反例として機能しているかの検算）。設計判断・文書の記述・保証範囲の明記など、**実行結果を伴わない指摘**には本ステップを適用しない——該当箇所を改稿したこと自体が対応であり、改稿後の記述を読み直して旧文言との矛盾が無いことを確認する等、指摘の性質に応じた確認で足りる。
3. **修正後の実測**: 修正を適用したスクリプトで同じフィクスチャを実行し、期待どおりの出力・終了値になることを確認する。
4. **回帰確認**: **正常系フィクスチャと、過去のラウンドで反例として使った全フィクスチャ**（合わせて「回帰集合」と呼ぶ）を同じ実行で再テストし、今回の修正が過去に直した反例を再び壊していないことを確認する。過去の反例がまだ無い初回ラウンドでは、候補が基本ケースで期待どおりの終了値になることを回帰集合の代わりに確認する。
5. **byte 一致の確認**: 候補本文へ修正を書き戻した後、**本文から再抽出したコード**が、実際に実行して確認したファイルと byte 一致することを機械的に検証する。
6. **記録は改稿の後**: §3-A の記録スクリプトは記録時点の提案 MD から `proposal_hash` を実測する。本節の改稿（打ち切り時の保証範囲明記を含む）は、**記録（§3-A）より前に完了させる**——記録後に改稿すると、記録済みの `proposal_hash` と現物が食い違い、レビュー記録が古い版を指したままになる。

この手順を踏まずに「Codex の指摘に対応した」とだけ `ccRebuttal` や findings 対応欄に書くと、対応が主張に留まり、対応漏れや修正自体が新たに持ち込むバグを機械的に検出できない。

**ラウンドを打ち切る判断（規模超過の検知）**: 指摘の性質が「軽量ツールの穴を塞ぐ」ものから「別の体系（例: CSS のカスケード規則・詳細度、フルパーサ相当の構文解析）を再実装する」ものへ質的に変化してきたら、それ以上の反復は候補の設計方針そのものを変える判断（＝軽量な補助ツールではなく本格的な処理系の実装）を要求している。そこで反復を打ち切り、残る指摘を `deferred` とする方針を決め、**候補本文に保証範囲の限界**（例: 「終了値 0 は何を意味し、何を意味しないか」）を明記したうえで、§3-A の記録スクリプトで記録する（Step 6 のとおり順序は改稿が先）。**ただし、残存する指摘が候補の主要目的そのものを損なう場合は打ち切りの対象にしない**——`deferred` は「周辺的な既知の限界」を人間の裁定へ送る手段であり、主要目的の未達を押し通す手段ではない。主要目的を満たせないと判断したら `needs-attention` のまま設計を見直す（§3-A の刈り取りに戻る）か、候補そのものを棄却する。この判断軸は `plan-review-convergence-loop` の「同一クラスの指摘が 2 巡続いたら列挙モード」とは別の軸（指摘クラスの反復回数ではなく、指摘が要求する実装の性質の変化）であり、対象が重なる場面では両方を併用してよい。

**検証用ファイルの扱い**: 本節の抽出・実行で作る一時ファイル（抽出したスクリプト・フィクスチャ・実行ログ）は、プロジェクトの working tree の外（スクラッチ領域）に置く。これらは §1 の調停（`marshal-review` が発火する実装変更）の対象ではない——working tree に対する変更ではなく、レビュー活動の一時的な副産物である。

### 3-B. 計画/設計レビュー → その場で提示・記録

findings をユーザーに提示し、当該 plan/報告書に記録する。候補レビューボックスは書かない（`request_id` が無いため）。

### 3-C. 経路が壊れた時 — 縮退の前に一度だけ切り分ける

呼び出しが 404 / 400 / 無応答になったら、§4 の縮退へ進む前に**一度だけ**診断する:

    node ~/.claude/scripts/codex-path-doctor.cjs

**上限は 1 回・5 分。** 診断が不能（スクリプト不在・無応答・上限到達・復旧できず）なら、
**その事由を記録して直ちに §4 へ進む。復旧の成功を縮退の条件にしない。**
§4 の「ブロックしない」は本節によって一切弱まらない。

診断は実体・ピン留め・疎通を実測し、**原因候補**と処方を出す（確定診断ではない）。
罠の詳細と処方はスクリプトの出力に載るので、**本節では列挙しない**。

**診断は設定を書き換えない。** 疎通したモデルが判っても、config への反映は
**人間が手で行う**（スクリプトは「どの行をどう直すか」を出すだけ）。疎通することは
**独立レビューに足る能力の保証ではない**ため、反映は既存の設定変更権限に従う。

## 4. レビュアー抽象化・縮退・最終権限

- **レビュアー抽象化:** `reviewerId` は自由文字列で、レビュアーエンジンを差し替え可能（既定 `codex`。別のレビュアー AI やローカル LLM でもよい）。Codex を本体にハードコードするな。
- **縮退:** Codex 不在／応答不能（§2 の 0 件、CLI 欠落、認証/ネットワーク失敗）の場合、**ブロックしない**。レビューは `pending` のまま（人間レビュー）にし、不在を記録 — 事由 + タイムスタンプ + 取った代替行動。本体は特定 AI 体制から独立を保つ。「if applicable」型の沈黙スキップ禁止。
- **最終権限は人間。** 本スキルは助言者。自動採用するな、Codex を最終審にするな。誤った reviewer verdict が無検証で通ってはならない。

## 5. 配布制約

レビュープロンプト・findings・記録物のいずれにも入れない:

- ユーザーの個人的固有名詞（人名・社名・プロジェクトコードネーム・製品名）、
- AI セッション命名や内部開発コードネーム。

技術的内容のみに留めること。

## Companion 安定呼び出し形（必須）

`codex-companion.mjs task` を呼ぶ際は次の形を厳守する:

    node <companion絶対パス> task --cwd <実在する絶対パス> --prompt-file <プロンプトの絶対パス> [--json]

- プロンプト本文を argv に直接渡さない（禁止: `task "<長文プロンプト>"` の単一引数形）。
  companion はサブコマンド後の argv が 1 要素だと shell 風に再トークン化し、本文中の
  `-C` 等の短フラグ風文字列をオプションとして誤パースする
  （実例: `git -C` 用例の引用 → `--cwd` 汚染 → 全 probe ENOENT → 「Codex CLI is not installed」誤報）。
- `--cwd` には必ず実在ディレクトリを明示する（argv が複数要素になり、再トークン化自体が構造的に不発になる）。
- プログラムから spawn する場合は `'node'` 文字列でなく `process.execPath` を使う（shim 解決揺れの回避）。
- 「Codex CLI is not installed or is missing required runtime support」に遭遇したら、
  インストール状態を疑う前に呼び出し形（単一引数プロンプト・不存在 cwd）を先に検査する。
