# golden 名前衝突 Proposal トリアージ

## 発火条件

- Skill Proposal の採用（adopt）を実行し、「adoption refused: '<name>' は golden 配布 skill と同名です」というトーストを受け取った時
- そのトーストに言及するユーザーコメントへ `proposal-comment-respond.cjs` で応答する時

## 前提として確認しておく実装（名称のみ挙げる。file:line は環境ごとに異なる）

- 採用処理の同名衝突ガード: 採用先ディレクトリ名が golden 配布 skill 名一覧に含まれる場合、有効な緊急 override が無い限り書込を拒否する（恒久シャドウ防止が目的）
- `EmergencyOverride`: 「golden バグ時のみ Doctor Analysis 動線で生成」を想定した型で、golden バージョンが前進すると自動失効する
- Doctor Analysis 画面の override 作成 UI 自身の説明文: 「golden skill にバグがあり同名の修正版を一時採用する必要がある時のみ使う」と用途を明記している
- golden の乖離判定（reconcile）ロジックは override レジストリを一切参照しない — override は採用時の書込ガードを一度通す資格にすぎず、golden 正本そのものを書き換えたり、golden 正本への恒久的な取り込みを保証したりはしない

**再確認条件**: 上記 4 点（衝突ガードの挙動・`EmergencyOverride` の失効条件・Doctor Analysis UI の文言・reconcile ロジックの参照有無）を変更する CCPIT 本体の改修を行った場合、本 skill のこの節と判定木を読み直して整合を取ること。

## 判定木

### 手順0. 前置判定 — この衝突は本当に「同一 skill の更新」を意図しているか

トーストが出た原因が「たまたま別目的の skill 名が golden と一致しただけ」であることがある。

- 提案内容が golden 側の既存の発火条件・振る舞いと無関係（同名だが別物）→ 本 skill の対象外。トーストの案内どおり提案 skill 名を変更する。ここで判定木は終わる。
- 調査しても同一性・更新意図が判断できない → **これ以上進めない**。提案者または golden 開発元へ追加情報を求め、経路選択を保留する。判断がつかないまま手順1以降へ進まない。
- 提案内容が golden 側の既存の振る舞いを変える/直す/拡張することを意図していると確認できた → 手順1へ進む。

### 手順1. バグ修正か、機能追加/改善か、分類できないか（ここでは操作の種類を選ぶだけで、まだ実行しない）

- **分類できない・両方の性質が混在する** → 安全側（機能追加/改善として扱う）。理由: override は「バグ修正のみ」という限定用途を持つ手段であり、疑わしい場合はその限定用途の外として扱う方が安全。操作の種類は「golden 正本の編集」を選ぶ。
- **golden 自体のバグ修正** → 操作の種類として「Doctor Analysis の緊急避難 override 作成」を候補にする。作成そのものは手順2（実行前ゲート）を通ってから行う。
- **機能追加/改善** → 操作の種類として「golden 正本の編集」を選ぶ。

いずれの場合も、この時点ではまだ override を作成せず、golden も編集しない。次に必ず手順2を通る。

### 手順2. 実行前の共通ゲート — 選んだ操作にかかわらず、実行前に必ず通る

手順1で選んだ操作が override 作成であっても golden 正本の編集であっても、実行前に次の両方を確認する。

**(a) 権限**: 「golden の開発元リポジトリで作業している」ことと「その操作を行ってよい権限がある」ことは別。

- 開発元リポジトリの外（実行主体がここにいない）→ その旨を明示し、golden 開発元のセッションでの実行が必要と報告して停止する。他プロジェクトの golden を代わりに編集せず、override も代わりに作成しない。
- 開発元リポジトリの中で、単独裁量の範囲内（例: 唯一の開発者兼運用者からその場で承認を得た）→ 実行してよい。
- 開発元リポジトリの中だが、承認権者が別にいる、または裁量の範囲が不明 → 自分で確定させない。変更内容（diff・override の理由・意図・影響範囲）をまとめた変更案を作成し、承認権者または開発元セッションへ引き継ぐ。

**(b) 独立レビュー**: 手順0・手順1の自己判定に**確信が持てない場合、または初めて扱うパターンの場合**は、実行に進む前に `codex-review` skill（計画/設計レビュー種別）で判定そのものを検証する。これは「毎回必ず行う自己確認」ではなく、「確信が持てない/初回のケースに限る条件付きの独立レビュー」である。過去の対応でも、結論自体は妥当でも理由付け（自動失効条件の解釈・経路の唯一性の主張範囲・分岐の網羅性）に補正が入った実績があるため、結論の当否だけでなく理由付けの精度も検証する。

(a)(b) をともに満たしたら実行する:

- **override 作成を選んだ場合**: 作成前に次の 3 点を確認する。1) 恒久修正（golden 側の是正）を待てない事情があり一時採用が実際に必要か 2) 対象 skill 名・現在の golden バージョンに対して override が有効に成立するか（`EmergencyOverride` の失効条件に照らして）3) 恒久修正までの追跡経路（誰が golden 側を直すか）が別途存在するか。3 点とも確認できれば作成する。1 つでも確認できなければ、override 作成を取りやめ「golden 正本の編集」へ操作を切り替えて本ゲートをやり直す。
- **golden 正本の編集を選んだ場合**: 実行手続きは `golden-distribution-safe-add` skill（正本特定・deploy 意味論の証明・正本/稼働環境のドリフト検知・追加ファイルと全置換対象の分離）に委譲する。本 skill はここまでの委譲判定を担い、編集の技術的手続き自体は重複実装しない。

## 提案コメントへの応答（`proposal-comment-respond.cjs` 使用時）

「既存スキルへの更新経路」を尋ねるコメントには、判定木を辿った結果を使って次の順で説明する:

1. 原因: 名前衝突ガードは意図的設計（恒久シャドウ防止）であり、アプリの不具合ではない
2. 手順1で選んだ操作の種類（override 作成 / golden 編集）とその理由
3. 手順2で実際に何を実行したか（override 作成・golden 編集・変更案の引き継ぎ・実行主体不在での停止・経路選択の保留のいずれか）
4. 残作業（golden 側の commit・配備検証は人間の手番であることが多い）

**decision と `adoption_label` の扱い**:

- `decision` は、コメントが求めた各要望が実際に何に反映されたかで個別に判定する。機械的に `declined` 固定にしない。提案 MD 本体（§3 の完成版テキスト）を改稿した場合は、その要望について `applied` にする。
- golden 正本を編集した場合、その事実を提案 MD へ追記するのは記録目的であり、それ自体は「提案内容の改稿」ではないので `applied` の理由にはしない。この場合の該当コメントの decision は、コメントが求めた「経路の実行」を満たせたかどうかで判定する。
- `adoption_label` を `reject`（経路変更の記録。内容否定ではない）に変更するのは、次の**両方**を満たした時点に限る: (i) golden 側の変更が検証済み（selftest 等）かつ配備を待つだけの状態になっている (ii) この提案全体（コメントで求められた要望全体）について、通常の adopt 経由ではなく golden 更新経路で扱うという処理方針が確定している。要望の一部だけが golden 側へ反映され、残りが未処理のままの場合は、未処理分を別提案へ切り出す、または `reject` にせず処理方針が確定するまで待つなど、扱いを先に確定させてからラベルを変更する。

## 禁止

- Doctor Analysis の緊急避難 override を、golden のバグ修正以外の目的（恒久的な機能追加等）に使わない
- 単独裁量の確認なしに、自分の判断だけで golden 正本を編集する
- 自分が開発元でない golden へ、提案内容を代わりに書き込まない
- `golden-distribution-safe-add` が扱うべき安全確認（deploy 意味論の証明・正本/稼働環境のドリフト検知等）を省略して golden を直接編集しない

## なぜ既存 skill への統合でなく独立 skill か

検討した代替案: `golden-distribution-safe-add` の入口に本判定木を追加する。採用しなかった理由は、`golden-distribution-safe-add` の発火条件が「追加作業の着手前」という、本 skill の手順0〜2（衝突の意図判定・override 誤用回避・権限確認）より後の段階を前提にしていることに加え、本 skill は CCPIT 固有の語彙（Doctor Analysis・Skill Proposal・`adoption_label`）に強く依存しており、混ぜると両 skill の汎用性を落とすため。独立させることで、`golden-distribution-safe-add` は引き続き「追加してよいと決まった後」の安全な追加手続きに専念できる。
