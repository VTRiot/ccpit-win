# memory-import-size-rotation — メモリファイルのログ退避ローテーション

## 発火条件

- ハーネスがメモリファイルの文字数上限の超過を警告したとき（執筆時点の文言の例: 「⚠ <file> is over the 40.0k-char limit」。上限の値と文言は版で変わりうる）。
- メモリファイル（CLAUDE.md / @import 先）の肥大に気づいたとき（定期点検を含む）。

## 背景

Claude Code は CLAUDE.md および @import 先メモリファイルに文字数上限を持つ。
超過分は切り捨てられ得るため、ファイル末尾のセクションが黙って読み込まれなくなるリスクがある。
肥大の典型要因は追記型ログ節（日次の動向・変更履歴など）の堆積。
これは LITM（長文中央の注意低下）とは別問題で、①毎セッションの無条件文字課金 ②物理的な読み込み欠落 の二重の実害を持つ。

## 手順

1. **計測**: 対象ファイルの総文字数と節ごとの内訳を出し、肥大源を特定する。上限を超えたかどうかの正は、ハーネスの警告そのものとする。計測は、肥大源の特定と、退避の後に余裕が取れたかの確かめに使う。
   **数えるのは文字数で、バイト数ではない。** 日本語など多バイト文字を含む UTF-8 の文書はバイト数が文字数を大きく上回るため、バイト数で測ると上限を超えていないのに退避してしまう。ハーネスの数え方に合わせて、ファイルの中身を文字列にしたときの JavaScript の `length`（UTF-16 の単位）で測る（パスは対象のファイルに置き換える）。これは、このスキルを書いた時点の版で確かめた実装の断片に基づく近い値で、BOM や改行の前段の処理まで含めた完全な一致は保証しない。
   例（Node）: `node -e "process.stdout.write(String(require('fs').readFileSync(process.argv[1],'utf8').length)+'\n')" '/path/to/CLAUDE.md'`
   例（PowerShell）: `(Get-Content -Raw -Encoding UTF8 -LiteralPath 'C:\path\to\CLAUDE.md').Length`
   （Windows PowerShell 5.1 は `-Encoding` を省くと BOM の無い UTF-8 を ANSI として読み、数を誤る）
   BOM 付きのファイルでは、Node の例は BOM を 1 文字として数え、PowerShell の例は数えないので、1 文字ずれる。ハーネスが読み込みの前段で BOM や改行をどう扱うかは確かめていないので、計測値で上限ちょうど付近の判断をしない（手順 6 の余裕で吸収し、際どいときはハーネスの警告で判断する）。
   ハーネスの数え方は、このスキルを書いた時点の Claude Code の実装の断片で確かめた（警告の文字数を、ファイルの中身の文字列の `length` で出している）。これは補助的な確かめで、実行形式や版によっては見つからない・読み違えうる。版が変わったら公式の情報を先に確かめ、食い違うときはハーネスの警告を正とする。補助の確かめ方の例: Claude Code の実行ファイルを `grep -a -o -E '.{0,200}char limit.{0,80}'` で探し、文字数を出している式を読む。
   `wc -m` や `awk` の `length` は、数え方がロケールや実装で変わる（ロケールが C のままだとバイトを数え、UTF-8 のロケールでも環境によって単位が違う）ので、上限との比べには使わない。使うのは、バイトを数えてしまっていないかの確かめだけにする（`printf 'あ' | LC_ALL=C.UTF-8 wc -m` が `1` ならロケールが効いている。`3` ならバイトを数えている。`C.UTF-8` が無い環境では、`locale -a` で名前に `utf8` か `UTF-8` を含むロケールを選んで同じように確かめる）。
2. **バックアップ**: `<file>.bak.<YYYYMMDD>_pre-slim` を作成する。
3. **退避**: 肥大源のログ行のうち直近 N 件（既定 10 件）を残し、それ以前を
   `ARCHIVE/<元ファイル名>_<内容>_<期間範囲>.md` へ **1 行も削らず**移す。
   `ARCHIVE/` は、プロジェクトに既にある退避用のフォルダを使う。無ければプロジェクトのルート（プロジェクトの CLAUDE.md がある場所）に作る。ユーザー全体の設定など、プロジェクトの外のファイルなら、対象ファイルと同じフォルダに作る。実行時のカレントディレクトリを基準にしない。
4. **ポインタ**: 元ファイルの当該節末尾に、退避先へのリンクを 1 行残す。リンクは元ファイルの場所から辿れる形（元ファイルからの相対パス、またはそのプロジェクトで使っているリンクの書き方）で書き、辿れることを確かめる。
5. **索引**: プロジェクトに索引ファイルがあれば退避先を登録し、更新日を更新する（無ければスキップ）。
6. **検証**: 総文字数が上限の 6〜7 割以下に収まったことを確認。行数規約など他のメモリ規約があればそれも満たすこと。
7. **commit / push**: 利用者が明示的に依頼・承認したときだけ行う。行う前に、並行セッションが動いている可能性があるため `git status` / `git log --oneline -3` で衝突・混入がないか確認し、対象のファイルを明示して commit する。

## 注意

- **削除はしない**。必ず ARCHIVE 退避＋ポインタ残置（情報量ゼロ損失）。
- 再発前提の運用として「ログが N 件を超えたら都度退避」の恒久ルール化を提案してよいが、
  standing rule の追加はユーザー判断（勝手にプロトコル文書へ焼き込まない）。
- 退避ファイル名に期間範囲（例: `_260620-260707`）を含め、後からの検索性を確保する。
