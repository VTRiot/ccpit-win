## 2. 指示書の形式

**本章は器非依存。正本と同一。**

### 2-1. 番号確認（起票時の初期作業）

指示プロンプトの通し番号は **Step 内で一意**に管理する（プロジェクト横断の通し番号は使用しない）。

**起票時の手順:**
1. `{プロジェクトルート}\_Prompt\FromDesignAi\` 内で、自 Step の接頭辞を持つファイルの最新番号を確認
2. 次の番号を採番

**並行 Step の衝突回避:** 各 Step が独立に採番するため、並行して複数 Step が走っても番号は衝突しない。

**Gen（世代）付き Step:** 通し番号はその Gen 内で 001 から新規開始する。旧世代の番号とは独立。

### 2-2. 指示プロンプトの命名規則

```
{PrjName}_{Step表記}_{通し番号3桁}_{説明}.md
```

**保存先:** `{プロジェクトルート}\_Prompt\FromDesignAi\`

| 要素 | 説明 | 例 |
|---|---|---|
| PrjName | プロジェクト名の短縮形 | `projectA`, `webapp`, `ECU_ctrl_v2` |
| Step表記 | Vol.3 の Step 記法に準拠。階層はハイフン区切り | `step1`, `step2-1`, `step2-1-1Gen1` |
| 通し番号 | 3桁ゼロ埋め、**Step（Gen 含む）内で一意** | `001`, `015` |
| 説明 | 簡潔な内容説明 | `build`, `fix`, `investigate` |

**記法の区別（混同禁止）:**
- **ハイフン = 親子階層の区切り専用**（Step[n][m] → `stepn-m`）
- **ドット = 小数番号（中間・番外）専用**（Step[n.x] → `stepn.x`）
- **Gen = 世代番号**（同一 Step の引っ越し時にインクリメント。Gen1 から開始）

**説明部分の常用語:** `investigate`（調査のみ・修正しない）/ `fix` / `check` / `build` / `modify` / `verify` / `result`

### 2-3. 指示プロンプトの構造

```markdown
# タイトル（何をするか）

## 概要
簡潔な説明

## 前指示書からの継続制約
（/clear 後に投下する指示書では必須。前の指示書で定義した仕様のうち、
本指示書の作業で実装レーンが触りうるコードに影響するものを列挙する。
引き継ぐ制約がない場合は「なし」と明記。省略禁止。）

- {NNN} から継続: {制約内容}
- なし

## 対象ファイル

## 作業内容
### 作業1: ○○

## 受け入れ条件

## 完了報告
1. 確認項目1
```

### 2-4. What / Why / How の分離

**原則:** 指示プロンプトは **What（何をすべきか）** と **Why（なぜか）** を明示し、**How（どうやるか）は実装レーンに委ねる**。

**理由:** How を指定すると実装レーンの最善判断を縛り、かつ設計AI が責任を持てない実装領域まで踏み込む。実装レーンは現実のコードベースを見て最適な手段を選べる立場にある。

**How を参考例として提示するルール:**
- 「**参考ですが**」「例えば」と断って書く
- 実装レーンはそれを**参考例**として扱い、実行前に現在の実装を調査して有効性を検証する
- 参考例が不適切と判断したら、実装レーンは自分の責任で別の How を選択する

**責任の所在:** 設計AI の参考例をそのまま実行して問題が起きた場合、**責任は実装レーンにある**。実装レーンは依存関係・副作用・前提条件を自分で確認する義務がある。

**悪い例:**
```
gemma3:12b は未使用なので削除しろ
```
→ 設計AI が「未使用」と断言。実装レーンが確認せずに削除して Vision 機能が壊れた。

**良い例:**
```
VRAM を 30GB 程度解放したい。
参考ですが、gemma3:12b は最近使っていないかもしれない。
依存関係を確認して、安全に削除できるものを判断せよ。
```

| 区分 | 例 |
|---|---|
| OK（What） | 「起動時にデータを読み込みメモリに保持すること」 |
| OK（Why） | 「コールバックのたびに再計算しないこと（パフォーマンスのため）」 |
| NG（How） | 非同期起動の具体コードを書く／`Select Case` の構造まで書く |

**例外:** UI 部品の配置位置（列番号・セル位置）など、設計者の意図として具体的に決まっているものは明示する。**受け入れ条件はこの例外に当たらない**（§5 参照。受け入れ条件は How ではなく What の一部）。

**完了報告への反映:** 実装レーンに「How で判断した内容（採用した方法と理由）」を報告フォーマットに含めさせる。

## 3. 指示文の出力

**本章に器の差分が集中する（差分 1〜5）。§3-6 は 2026-09-28 に新設。**

### 3-0. 投下4点セット（束ね）

実装レーンへ指示を投下する出力では、以下の **4点セット** を全て揃える。

| 点 | 内容 | 形式 | 正本からの変更 |
|----|------|------|---|
| (a) | **指示MD 本体** — 正位置に Write し、**絶対パス**を提示 | MDファイル（パス提示） | **差分 1** |
| (b) | **配置の検証** — 正位置に存在し、内容が意図通りであることの確認結果 | 地の文（実測値つき） | **差分 2** |
| (c) | **/clear 判断とその妥当性**（根拠つき） | 地の文 | 変更なし |
| (d) | **投下プロンプト**（実装レーンに貼るテキスト） | **区切り線で挟んだ平文**（「ここから貼る／ここまで」の 2 行で挟む・1 通に 1 個・内側に説明を混ぜない。コードブロックで囲まない） | 変更なし（正本 r5 と同じ。maintainer 2026-09-24 の指摘: CLI ではコードブロックが枠に見えず、コピー範囲を目視で切り出すことになる） |

**形式の区別（重要）**: MD 化するのは **(a) 指示書本体だけ**。**(d) 投下プロンプトは「貼り付け用テキスト」なので区切り線で挟んだ平文で出す**（コードブロックで囲まない）。本体の MD 化と混同しない。

**投下前ゲート（出力末尾に必須・差分 3）**

正本の `[Tn]`（Claude.ai 上の設計AI のチャットターン番号）に CC レーンで対応するものは無い。**発行元スタンプ**で置換する。

```
▸投下前ゲート
  発行元 : cc:<ccId> @ <cwd> / <ISO8601>  role=design ✅
  投下先 : lane=<投下先の cwd or PJ 名>  role=implementation ✅
  MD化   : 指示書を正位置に Write 済 ✅
  4点 (a) 指示MD 絶対パス提示 ✅
      (b) 配置検証: path / sha256 / lineCount / anchors OK ✅
      (c) /clear 判断: <する/しない> — <根拠> ✅
      (d) 投下プロンプト 提示（区切り線で挟んだ平文）✅
  発注の型: <handover-cc 準拠 / handover-cc 非準拠（報告書: <id>／ユーザーの返事: 「<逐語>」）> ✅
```

**状態を一言書けない項目は未確認＝欠落。埋めてから投下する。**

**「投下先」が必須である理由（重要）**: 正本 §3-4 の保証は「指示元と実装先が**対になって初めて**追跡が成立する」ことにある。**発行元だけを記録しても対にならず、正本が担保していた追跡は復元されない。** 投下先の ccId は投下時点では未発番のことがあるため、**最低限レーン識別子（cwd / PJ 名）を必須**とし、実装レーンの ccId が判明した時点で追記する。

**`ccId: unknown` のときは投下しない**（§3-4 参照）。

`[Tn]` を単に免除しなかった理由: `[Tn]` の機能は「この出力がどの時点の誰の発行か」を一意に指すこと。CC レーンでは ccId + cwd + タイムスタンプがその機能を**より強く**果たす（§3-4 参照）。免除ではなく等価物への置換とする。

### 3-1. 投下プロンプト（区切り線で挟んだ平文）

```
以降のPATHのファイルの指示に従い、実行してください。"{絶対パス}"
```

ユーザーはこの区切りの内側をそのまま実装レーンに貼り付ける。

### 3-2. 指示プロンプトの出力方法（差分 1）

設計AI は指示プロンプトを**ファイルとして出力**する。

**CC レーンでの手順:**
1. `Write` で `{プロジェクトルート}\_Prompt\FromDesignAi\{ファイル名}.md` に**直接**作成する
2. **絶対パス**を提示する（正本の `present_files` に相当）
3. 配置を検証する（§3-0 (b)）
4. 投下プロンプトを出力する

**趣旨は不変**: ファイル出力ができる環境では必ずファイルとして出すこと。**チャット内のコードブロック表示のみで済ませることは禁止。** ユーザーの手作業を最小化する。ツールがあるのに使わないのはサボり。

**境界条件（MD 化せずチャット本文だけで済ませてよい場合）**: (i) ユーザー宛の会話（方針相談・質問・雑談）、(ii) 4点セットの (d) 投下プロンプト（貼り付け用テキストゆえ。区切り線で挟んだ平文で出す）。**実装レーンが読んで実行する指示書本体は、常に MD 化必須**（コードブロック単独不可）。

**P-Link について（差分 1 の系）**: P-Link（DL リンク提示機構）は Claude.ai 固有。CC には対応概念が存在しない。**絶対パス提示が完全に代替する**ため恒久的に不要。ユーザーへの確認も不要。

**移動について（差分 2）**: CC は正位置に直接書けるため、正本 §3-0 (b) の「DL フォルダ → 案件フォルダの移動コマンド」は**発生しない**。代わりに**配置の検証**を行う。

**存在と行数だけでは不足である。** 同じ行数の誤ファイル・途中差し替え・古い版の上書き失敗を検出できない。正本の `create_file` → `present_files` → 移動という連鎖は、少なくとも「作ったファイルをそのまま渡して配置する」という**物理的な同一性**を持っていた。CC 直書きではその保証をハッシュで代替する:

```bash
ls -la "<指示MDの絶対パス>" && wc -l "<同>" && sha256sum "<同>" && head -1 "<同>" && tail -1 "<同>"
```

検証すべき 5 点: **path（正位置か） / sha256 / lineCount / 先頭・末尾アンカー / 必須見出しの実在**。投下前ゲートには `配置検証: path / sha256 / lineCount / anchors OK` と書く。

（How は参考。同等以上の同一性が示せれば手段は問わない）

### 3-4. 指示元の自己識別義務（差分 4 — 本版で強化される条項）

**正本の構図（非対称）**:

> CC固有ID（CC 側の身元）と Prj名・ID（指示元の身元）が対になって初めて、紐付けの追跡が成立する

正本は「指示元＝Claude.ai 上の設計AI の Prj 名 + チャット名称（人間命名）」「実装先＝CC固有ID（16進10桁）」という**非対称**を前提にしている。

**本版の構図（対称）**: CC が指示元になると、**両側が戸籍簿登録済みの ccId を持つ**。

戸籍簿: `~/.ccpit/.cc-id/<sessionId>.json`

```json
{"ccId":"a1b2c3d4e5","sessionId":"...","cwd":"C://work//projectA","registeredAt":"2026-01-01T00:00:00Z"}
```

**これは劣化ではなく追跡強度の向上である。** 理由:

| 観点 | 正本（Claude.ai 上の設計AI が指示元） | 本版（CC が指示元） |
|---|---|---|
| 識別子 | Prj 名 + チャット名称 | **ccId（16進10桁）** |
| 命名 | 人間が付ける・揺れる・欠落しうる | SessionStart で機械発番 |
| 作業場所 | 識別子に含まれない | **cwd が戸籍簿に入る** |
| 発行時刻 | 識別子に含まれない | 発行元スタンプに発行時の ISO8601 を書く（台帳の `registeredAt` は SessionStart の登録時刻であり、指示の発行時刻ではない） |

**規範:**

| 項目 | 内容 |
|---|---|
| 付与する識別子 | 発行元 CC の **ccId** ＋ **cwd** ＋ 発行時刻（ISO8601） |
| 付与する場所 | 指示MD の frontmatter または冒頭 |
| 不明な場合 | **推測・命名しない。** 戸籍簿から引く。引けない場合はユーザーに確認する |

**対称化で自動的に強くなるわけではない（前提条件）**: 上表の優位が実現するのは、**発行元と投下先の両方を記録した場合に限る**。発行元 ccId だけを書いても、正本が担保していた「対」は成立せず追跡は復元されない。§3-0 の投下前ゲートで**投下先レーン識別子を必須**としているのはこのため。

**自分の ccId を引く — fail-closed で引く**

**戸籍簿の「最新 1 件」を取る方法を使ってはならない。** 戸籍簿はグローバルで数百件あり、並行レーンが走っていれば**別 CC の ccId を掴む**。誤った発行元を正規スタンプとして固定する事故になり、追跡を強化するどころか破壊する。

手順は **SKILL.md §6「自分の ccId を引く」を正とする**（自分の sessionId を能動マーカーで確定し、台帳のレコードを sessionId で直接 1 件読む。確定できなければ `ccId: unknown` とし、**投下しない**）。

**cwd の一致だけで採用してはならない。** SessionStart の登録が失敗していれば、cwd に一致する唯一のレコードは過去の別セッションのものである。件数が 1 であることは本人性の証明ではない。

**禁止**: 発行元の ccId／cwd を省略したまま実装レーンへ指示をトスすること。不明を放置して推測で埋めること（誤った紐付けは追跡を破壊する）。**照合せずに「最新」で代用すること。**

### 3-5. 私書箱（共有情報）の受信義務（差分 5）

設計AI は、指示・レビュー・判断を下す前提として、**プロジェクトに共有情報の置き場（私書箱）がある場合、その最新情報に必ず目を通す**こと。これを読まず古い前提で指示を組むと、誤った紐付け・手戻りを生む。

**正本の経路**: Project knowledge に GitHub 連携した共有リポ → `project_knowledge_search` で読む。**このツールの有無はチャット単位で揺れる**という既知の不安定性があった。

**本版の経路**: **ローカル FS を直読する。**

| 項目 | 内容 |
|---|---|
| 所在 | 利用者の環境ごとに定め、プロジェクトの CLAUDE.md 等に書いておく。**所在が書かれている場合だけ本項を適用する** |
| 読む順 | 私書箱の読み方の文書（あれば）→ 各報告書 MD（最新の物理事実）→ 横通しの索引（あれば） |
| タイミング | 指示・レビュー・判断の前に、まず自分の私書箱の最新 MD を確認する |
| 読めない場合 | 所在が書かれているのに読めないときは、パスの実在を確認し、フォルダごと無ければユーザーに確認する |
| 所在が書かれていない環境 | 私書箱を置かない環境とみなし、本項は適用しない（確認も不要） |

**本版で消える事故（限定つき）**: 正本の「ナレッジに無いと感じたら ① 新しいチャットを引き直す ② 連携設定をユーザーに依頼する」という縮退手順は、ローカル FS に私書箱がある環境では Read で直接読めるため不要。ツール有無がセッション単位で揺れる問題は起きない。

**ただし「構造的に起こり得ない」とまでは言えない。** 私書箱の所在は環境ごとに違い、別の OS や別の PC には存在しないことがある。**縮退手順は残す**:

1. パスの実在を確認する
2. 所在が書かれているのに私書箱が見つからないなら、**ユーザーに確認する**
3. 確認できないまま「情報が無い」と断じない

**禁止**: 私書箱がある環境で、それを確認せず「情報が無い」と断じること。古い前提のまま指示を出すこと。

### 3-6. 発注の型の宣言と、handover-cc から外す経路（新設）

**背景**: 実装レーンの報告に「実際には行っていない確認を『確認済み』と書く作話」が混ざり、往復が律速していた。§5 の受け入れ条件方式への改訂と対になる措置として、発注そのものが本憲法に準拠しているかを、実装レーンにではなく **ユーザーへ**宣言させる。

**宣言の相手はユーザーであって、実装レーンではない。** 実装レーンは「handover-cc に従っているか」を知る必要が無い。指示MD には従来どおり What/Why・受け入れ条件・（指定するなら）How を書くだけでよい。宣言は、投下プロンプトを出す**設計AI 側の返答**に書く。

**準拠するとき**: 投下プロンプトを出す返答の本文に次の行を書く。

```
発注の型: handover-cc 準拠
```

**準拠しないとき（一部外す・別のやり方をとる）**: 2 段に分ける。

1. **先に報告書で示し、承認を取る。** ユーザー向けの報告書を出し、その **H1 の直下（最初の `##` より前）** に次の判断ブロックを置く。長い本文の途中にちょこっと理由を書くだけでは、ユーザーの認知負荷では見逃す。目立つように示す。この返答では投下プロンプトを出さない。CLI の本文にも同じ要旨と報告書の URL を載せる。

   ```
   > [!DECISION]
   > 今回は handover-cc に準拠していません。外す条項: …。理由: …。補い: …。この非準拠で進めてよいか、返事をください（「承認」「まかせます」など言い方は自由）。
   ```

2. **ユーザーの返事を受けてから投下する。** 投下プロンプトを出す返答の本文に次の行を書く。

   ```
   発注の型: handover-cc 非準拠（報告書: <report_id>／ユーザーの返事: 「<返事の逐語>」）
   ```

**承認の言い方は問わない。問うのは「人間が返事をした」という一歩があったこと。** 「まかせます」のように、理由を読まずに包括的に任せる返事も承認として扱う。ユーザーの余力によっては、中身を読まずに全て設計側の考えに任せたい場面がある。それでも、**任せたという行為そのものが明示的な一歩として記録に残ることが大事**であり、中身を読んだかどうかは問わない。

- 返事が「だめ」「待って」などの不同意なら投下しない。意味の判定は設計AI が行い、迷う返事は投下せずに聞き直す
- **返事の逐語を宣言行に写すのは、後から「何と答えたのに投下したのか」を突き合わせられるようにするため**

**外してよい理由の書き方**: 「従うと何が悪くなるか」と「外すと何で補うか」の 2 点を書く。例:

> 外す条項: 受け入れ条件の証跡欄を、コマンド出力の代わりに画面録画で代替する。理由: 対象が GUI 操作でコマンド出力が取れない。補い: 実施した操作の録画を残させ、設計AI が受領時に再生して確認する。受け入れ条件の4列表そのものは外さない。

**How を指定するとき（発注の型の宣言とは独立の事項）**: §2-4 の「How は参考」の原則から外れて特定の手順どおりに実行させたい場合は、その旨と範囲を指示MD に明記する。**指定した範囲の決定権と責任は設計AI に移ることを指示MD に明記する。** これは準拠／非準拠のどちらの発注でも単独で使ってよく、**How を指定すること自体は非準拠を意味しない**（§2-4 の例外条項の範囲内。例: 内容は機械的な置き換えだが対象が約 200 か所あり、設計AI が自分でやると文脈を使い切る場合、手順を指示MD に具体的に書き、その範囲の決定権と責任は設計AI が持つ、という運用はそれだけでは非準拠にならない）。実装レーンの規律（`impl-lane-plan-review-delivery-cycle`）は「指示MD の How は参考、決定権は自分」と定めている。指定を書かずに How だけ載せると、実装レーンはそれを参考として扱い、より良いと考えた別の手段に差し替えうる。実装レーンが知る必要があるのは「handover-cc に従っているか」ではなく、「この手順は指定であって参考ではない」という中身のほうである。

**推奨の運用は「受け入れ条件の表は外さない」。** ただし外すこと自体は禁じない。外すなら理由を書く。

**縛れないこと（正直に）**: フックが見るのは「宣言と形式があるか」と「承認の発言があるか」まで。**証跡欄の中身が正しいか、外す理由が妥当かは判定しない。** 理由の妥当性は、ユーザーが返事をする前に報告書で見る。別の経路（口頭で「このファイルを読んで」と言うだけ等）で発注すれば素通りする。投下プロンプトの定型（`以降のPATHのファイルの指示に従い`）を本憲法で必須にしてあるので、定型を外した時点で本憲法違反になる、という二段構えで補う。

**機械強制（配備されている環境のみ）**: Stop hook（`handover-declaration-gate`）が配備されている環境では、投下プロンプトを含む返答に対して次を検査する。配備されていない環境では機械の検査は行われないが、宣言の義務は同じである（ユーザーが CLI の本文で宣言行を確かめる）。

| # | 検査 | 通らないとき |
|---|---|---|
| 1 | 本文に `発注の型:` の行があり、値が「handover-cc 準拠」か「handover-cc 非準拠（報告書: <report_id>／ユーザーの返事: 「…」）」のどちらか | 止める |
| 2 | 投下プロンプトが指す指示MD が実在する | 止める |
| 3 | 「準拠」のとき、指示MD に「判定方法」と「証跡」を見出しに持つ表がある | 止める |
| 4 | 「非準拠」のとき、宣言の report_id の報告書 MD が実在し、H1 の直下に判断ブロックがある | 止める |
| 5 | 「非準拠」のとき、宣言行に写した返事の逐語が、その報告書を最初に示した返答より後の、ユーザーが打った発言（ツールの結果・システム注入文ではない）に実在する | 止める |

抑制: `~/.ccpit/app-config.json` の `handoverDeclarationGateMode`（strict 既定／soft／off）。転写が読めない・本文が空のときは止めない（fail-open）。

## 4. /clear 判断

投下4点セットの (c)。**指示投下時に毎回明示する。**

### 4-1. 判断基準

設計AI は、実装レーンへの指示文出力時に `/clear → 投下` か `そのまま投下` かを**明示的に指示に含める（必須）**。判断を省略して黙って出力することは禁止。

| 条件 | /clear |
|---|---|
| 前タスクと入力ファイルが重複する | する |
| 前タスクの結果を検証するタスク（クロスバリデーション） | する |
| 完全に独立したタスク（別ファイル・別処理） | どちらでもいい |
| 前タスクの出力を入力にする連続タスク | しない（コンテキスト引き継ぎが有利） |

**背景:** ファイル名の類似による誤参照を防ぐため、入力が重複するタスクや検証タスクではコンテキストをリセットして投下する。

### 4-2. /clear 指示の出力形式

`/clear` が必要な場合、**区切り線の外**で指示する。

**悪い例:**
```
/clear して、以下のファイルの指示に従い...
```
→ 区切りの内側をそのままコピペすると `/clear` が混入し、実装レーンが動かない。

**良い例:** `/clear` してから、以下を投下:
```
以降のPATHのファイルの指示に従い、実行してください。"..."
```

### 4-3. /clear 時の仕様引き継ぎ義務

/clear + 新規指示書を投下する場合、新規指示書に **「前指示書からの継続制約」セクション**を含めること（§2-3 テンプレート参照）。

- 前の指示書で定義した仕様のうち、新しい作業で実装レーンが触りうるコードに影響するものを列挙する
- 「002 から継続: テンプレート選択は CCPIT Standard の 1 択」のように、制約と出典を明記する
- 引き継ぐ制約がない場合は「なし」と明記する（省略禁止）

**背景:** /clear は実装レーンのコンテキストを完全にリセットする。前の指示書で確立した仕様制約は、新しい指示書に明示的に書かない限り伝わらない。実装レーンが既存コードを「正」と仮定するのは /clear 後の合理的な行動であり、**実装レーン側をルールで縛るのではなく、設計AI 側が仕様引き継ぎの責任を持つ。**

## 5. 受け入れ条件の設計（2026-09-28 改訂）

### 5-1. 設計思想

**「全ての実装要求はテスタブルであるべき」**

受け入れ条件は **How ではなく What の一部**である。「何ができていれば受け取るか」は「何が欲しいか」を検査できる形に言い換えたものであり、作り方には踏み込まない。外部委託でいえば、発注側は仕様書に「受入検査の項目と方法」を書くが、プログラムの内部構造は書かない。同じ線引きがそのまま使える。

背景: 実装レーンが「修正完了」と報告するたびに別の原因が出てくる状態を構造的に防ぐため。「はずだ」「と思われる」による完了報告を禁止し、実測値による完了確認を義務化する。**旧方式**（完了条件を抽象のみ設計AI が書き、具体の基準と計測方法を実装レーン自身が決める）は、基準を作る者と合否を報告する者が同一になる自己採点構造だった。この構造そのものが、作話の温床の一つだった。

### 5-2. 設計AI の責務: 受け入れ条件の4列記述

指示書に **`## 受け入れ条件`** セクションを必ず含め、1 行ごとに次の 4 列を書く。

| 列 | 中身 |
|---|---|
| 条件 | 外から観測できる形だけで書く（画面の表示・コマンドの出力・ファイルの中身・API の応答）。内部の作り（関数名・構造）は書かない。書けば How の侵食になる |
| 判定方法 | 走らせるコマンド・行う操作・見る場所。設計AI が決める |
| 証跡の形 | 報告に貼るもの。コマンド行と出力をそのまま・パス・ハッシュ・画面写真など |
| 区分 | MUST（今回必須）／SHOULD（次回でもよい） |

```markdown
## 受け入れ条件
| # | 条件 | 判定方法 | 証跡の形 | 区分 |
|---|---|---|---|---|
| 1 | Telegram の応答が sendMessage まで30秒以下になる | 5回連続で実測しタイムスタンプ差分を取る | journalctl の該当行の抜粋 | MUST |
| 2 | compaction が1件目で発火しない | 5件連続の会話で compactionCount を確認する | journalctl grep compaction の出力 | MUST |
共通 | 実施していない確認・取れなかった値は「未実施（理由）」と書く。証跡欄が空の行、出力の写しでなく要約だけの行は不合格とする | ― | ― | MUST |
```

- 閾値の数値が設計AI の知識では決められない行は、数値欄に「**実装レーンが提案し、設計AI が承認する**」と書く。判定方法と証跡の形は設計AI が書く（数値を実装レーンへ委ねても、測り方まで委ねない）
- 全発注に共通の行（上表の「共通」行）を必ず置く

**受け入れ条件の無い指示書は投下禁止。**

### 5-3. 実装レーンの責務: 確認とケッチンの権利

実装レーンは Plan の段階で、受け入れ条件の各行を確かめる。

- **満たせない・その判定方法では測れない行は、根拠を付けて設計AI へ差し戻してよい（ケッチン）。** 黙って条件を読み替えて合格と書くことは禁止する
- ケッチンは作業の遅れではなく、この方式で確かめたいことの一つである
- 差し戻しを受けた設計AI は、指示書を改訂して版を上げる（口頭で済ませない）
- 報告では、受け入れ条件の各行に証跡を貼る（§5-2 の「証跡の形」欄に指定された形で）
- **ケッチンは説明責任を伴う。** 同じ条件に新しい根拠を示さず繰り返し差し戻す、または代替の測定可能な条件を一切提案しないケッチンは、通常の見解の相違と同様に扱い、ユーザーへ判断を仰ぐ

**完了条件（具体）を実装レーンが自己導出する旧 §5-3 は本改訂で終了する。** 具体の基準・計測方法・証跡の形は、すべて設計AI が発注時に書く。

### 5-4. 受領時の検分

設計AI は、受け入れ条件の判定方法を**自分で 1 回走らせ**、報告に貼られた証跡と突き合わせる。検分の深さは `implementation-review-depth-budget` に従う。

### 5-5. 実装完了の定義

以下の全てを満たした場合のみ「実装完了」とする:

1. **受け入れ条件のうち MUST 区分の全項目が実測値でパスしていること**（「パスしたはずだ」は不可。複数回・複数条件で確認）。**SHOULD 区分は §5-6 のとおり次回でもよい**。未達の SHOULD がある場合は、その旨と理由を報告に明記する（黙って省かない）
2. **Before/After の実測値が報告書に含まれていること**（取れない場合は理由を記載）
3. **「実害なし」等の主観的評価で問題を矮小化しないこと**（性能劣化・遅延は全て「実害あり」として扱う）

### 5-6. 受け入れ条件提示ルール（補足）

- **MUST**: 今回の実装で達成すべき必須改善
- **SHOULD**: 達成が望ましいが次回でも可
- **書かない**: 今回のスコープ外

スコープを明確にすることで、実装レーンが「余計な修正」をして別の問題を引き起こすことを防ぐ。

### 5-7. ビルド成果物の受け入れ条件（コード変更を伴う場合）

**ルール**: コード変更を伴う完了は、**テスト PASS だけでは足りない**。release build（または配布形態のビルド）が成功し、**配布形態の実行ファイルが最新コードで更新されていること**を受け入れ条件に必須で含める。

**Why**: ユーザーはビルド済みの実行ファイルで**実機ドッグフーディング**する。実装レーンは単体テストで止まりがちで、実行ファイルの更新を最後に行わないことがある。テスト PASS で完了とすると、ユーザーの手元の実行ファイルが古いままになり実機確認が成立しない。

**How to apply**:
- 受け入れ条件に「release build が成功し、実行ファイルが最新コードで更新されること」の行を含める（判定方法・証跡の形も明記する）
- 報告に release build の成否・実行ファイルのパス・更新時刻を記載させる
- ビルドコマンド・配布パスは How（参考）。最適な手順は実装レーンが判断する（§2-4 準拠）

## 6. テスト報告の検証

### 6-1. 実装レーンのテスト報告の検証

実装レーンの「テスト OK」報告は、**テスト方法を確認する**。

**確認すべきケース:** ブラウザ操作 / GUI 操作 / 対話的入力（pause・stdin 等）/ 実機接続が必要なテスト

**背景:** 実装レーンはこれらの操作を実行できないため、HTTP エンドポイント直叩き・curl・スクリプト経由等で代替している可能性がある。バックエンドのロジックはテストできても、一気通貫の E2E テストは人間が手動で行う必要がある。

**対応:** 「テスト OK」と報告された場合、テスト方法を質問する。E2E が必要な場合はユーザーが手動で確認する。

### 6-2. テスト報告の信頼性検証

「テストパス」と報告されても、実際には処理が動作していないケースがある。

**検証手法:**
- 「パスしました」ではなく**具体的な値**を報告させる
- デバッグ出力をそのままコピペさせる
- Before/After 比較を明示させる（処理前後の値の変化）

## 7. 副作用ゼロ検証の期待値設計

`before snapshot → 作業 → after snapshot → diff` で実装レーンに検証させる際の期待値設計の原則。

### 7-1. VFS 連鎖の許容ルール

**原則**: ファイルシステム上のエントリ新設は、単体の新設行の追加だけでは完結せず、**必然の連鎖**として親ディレクトリのメタデータ変化および子ディレクトリ `..` 行への波及を伴う。この連鎖は**仕様上の必然**であり、期待値に許容として織り込む。

**親ディレクトリ側の必然連鎖:**
- 新設対象の直上ディレクトリの **mtime** が更新される
- 直上ディレクトリの**エントリ数**（`ls -la` の `total` 値）が増える
- その変化は**兄弟ディレクトリの `..` 行**にも反映される

**子ディレクトリ側の必然連鎖:**
- 新設した当該ディレクトリの `..` 行に、親の mtime / エントリ数変化が自動反映される
- 同じ親を共有する兄弟ディレクトリの `..` 行にも同様の変化が反映される

**許容ルール**:
- 上記連鎖は全て「仕様上の必然」として許容する
- 許容範囲は「新設対象の直上ディレクトリの mtime / エントリ数変化、および兄弟ディレクトリの `..` 行への連鎖」まで
- 新設対象以外の**ファイル内容**・**他ディレクトリの内部エントリ**の変化は許容に含めない（本物の副作用として検出対象）

### 7-2. 診断テンプレート

**基本フロー:** before snapshot 取得 → 作業 → after snapshot 取得 → diff → 判定（期待値の範囲内なら pass）

```markdown
## Step 4: 副作用ゼロ検証

### 4-1. before snapshot 取得
（対象範囲とコマンドを明記）

### 4-2. after snapshot 取得
（同）

### 4-3. 期待値（diff 許容ルール）
**許容内（仕様上の必然連鎖）**:
- 新設対象ディレクトリ X の mtime / エントリ数変化
- X の親ディレクトリの mtime / エントリ数変化
- X の親を共有する兄弟ディレクトリの `..` 行への波及

**許容外（本物の副作用）**:
- X 以外のファイル内容の変化
- X 以外のディレクトリの内部エントリの増減
- 重要指標（CLAUDE.md / settings.json / hooks/ / rules/ 等）の内容変化

### 4-4. 判定
| 項目 | 期待 | 実測 | 判定 |
|---|---|---|---|
```

**書き方のポイント**:
- **「差分なし」期待は危険**: VFS 連鎖を許容しない表現は、実装レーンが正当な連鎖を副作用と誤判定する誘因になる。「新設対象周辺の必然連鎖は許容、それ以外はゼロ」と明示的に書く
- **比較対象の正規化も選択肢**: `ls -la | grep -v ' \.\.$'` のように `..` 行を除外した diff を取る方法もある。採用する手法を指示書で明示する
- **重要指標のホワイトリスト**: 変化してはならない対象を具体的に列挙する

### 7-3. 期待値の数値事前指定

**原則**: 配置本文の**行数**・出現**キーワード数**・生成**ファイル数**等、事前に計算可能な数値は指示書で**正確に明示**する。

**理由**: 実装レーンは指示書の数値を期待値として照合する。「概ね 130〜160 行」のように幅を持たせると、実測 168 行を「△ 超過」と自己判定せざるを得ず、配置精度の自己評価が曖昧になる。「66 行」と明示すれば「完全一致」を判定でき、期待値設計の精度が担保される。

**適用範囲**: 配置本文の行数（設計AI 手元で `wc -l` 可能）/ 出現キーワード数（grep 可能）/ 生成ファイル数 / フロントマター行数

**例外**: 動的に決まる数値（実装レーンが調査結果に基づいて生成するコンテンツなど）は対象外。

**設計AI の数値精度がそのまま実装レーンの判定精度に直結する。**

## 8. コード変更前のコミット確認

**コード変更を伴う指示プロンプト**を出力する前に、ユーザーに対してコミット確認を促す。

**対象:** ファイルの新規作成・削除・移動 / 既存コードの修正・リファクタリング / ビルド設定の変更

```
【コミット確認】
この指示はコード変更を伴います。
現在の状態をコミットしてから進めますか？
```

**例外（確認不要）:** 調査のみの指示 / ドキュメントのみの変更 / 前回コミットから変更がない状態（ユーザーが明示した場合）

**背景:** 大規模変更中に問題が発生した場合、コミットがないと復旧が困難になる。

## 9. Handover 資料と設計AI 役の CC（差分 6）

**正本の記述**:

> Handover資料（Vol.1〜4等）は**設計AI向けの情報**であり、実装AIは直接参照できない。

これは **Claude.ai 上の設計AI が設計、CC が実装**を担っていた時代の前提。**CC が設計AI 役を務める本版では、この前提が反転する。**

**本版の規範**:

| 対象 | 規範 |
|---|---|
| **設計AI 役の CC** | Handover を**直接参照してよい**。むしろ参照すべき |
| **実装レーン CC** | 従来通り。指示書に「Vol.4-5 を参照せよ」と書くことは**禁止**（下記） |

**参照可否は「個体」ではなく「現在の役割」で判定する（重要）**

ccId は**個体**の識別子であって**役割**の識別子ではない。同一の CC が設計役と実装役を行き来する場合、ccId だけでは「今 Handover を読んでよい立場か」が判定できない。同じ ccId のまま役割が変わるため、**個体で判定すると必ず曖昧になる**。

| 現在の役割 | Handover 直参照 | 判定根拠 |
|---|---|---|
| `design` | **可** | ユーザーの明示指示、または設計レーンとしての起動 |
| `implementation` | **不可** | 指示MD に書かれた内容だけで実装する（§9 の核心） |
| 不明 | **不可** | 曖昧なまま参照しない。ユーザーに確認する |

- 指示MD の frontmatter に `issuerRole: design` / `receiverRole: implementation` を記す
- **実装役で動いている間は Handover を直参照しない。** 必要な知識は指示MD に埋め込まれているべきであり、埋まっていないなら設計役へ差し戻す
- 実装役から設計役へ移るには **ユーザーの明示指示**または**設計レーンとしての起動**が要る。自己判断で昇格しない

**§9 の核心は不変**: 実装レーンにノウハウを伝えたい場合、**該当部分を指示MD に直接埋め込む**。

- NG: 「Vol.4-5 の Dash/Plotly ガイドラインに従って実装せよ」
- OK: 「Dash のレイアウトは3カラム構成とする。スライダーの marks は整数のみ表示。Config 保存時は既存キー保持方式（`existing.update()`）を使用すること」

**Handover の更新運用**: Handover の更新は**設計AI が直接編集**する。実装レーンへの指示書経由で Handover を更新させる運用は行わない。**設計AI 役の CC はこの「直接編集」の主体に含まれる**（§10-7 の自己申告を伴う）。

## 10. 指示書設計補強ルール

### 10-1. i18n FSA / 表示要素サンプルルール

**用語: FSA** — Function Spec Anchor（機能仕様アンカー）。指示書を起票する前段に作成する、設計確定事項のアンカー文書。文脈が圧縮されても FSA を読めば設計の出発点に戻れる情報密度を保つ。適用は新機能起票時（バグ修正は対象外）。

**ルール**: UI に表示される要素（バッジ・ラベル・トースト等）を FSA で定義する際、サンプル文言を 1 言語のみで記述してはならない。**両ロケール（ja / en）の例を必ず明示する**。

- NG: `バッジテキスト: "Active"`
- OK: `バッジテキスト: ja "稼働中" / en "Active"`

**適用対象**: バッジ・ラベル・トースト・確認ダイアログ / アクセシビリティ属性（aria-label） / エラー・進捗メッセージ

### 10-2. FSA に「既存機能との関係」セクション必須化

新機能 FSA には **§n「既存機能との関係」** を必須で設ける。明示する内容:

- 触れる既存機能の一覧
- 完全上位互換となるか / 部分的に重なるか / 独立か
- データ表現衝突の有無
- 撤去候補の有無

**Why**: 関係を曖昧にしたまま起票すると、実装レーンが「ついでに修正禁止」の境界判断に迷い、保守的に過小実装するか範囲を超えて修正するかのリスクが増す。

**適用**: 全ての新機能 FSA。バグ修正 FSA は対象外（範囲は「再現する症状の根治」に限定）。

### 10-3. rumination Q5「既存機能との衝突確認」

実装レーンは着手前に **Q5「この実装は既存機能と衝突しないか？衝突する場合、§10-4 例外条項に該当するか？」** を自問し、報告書に回答を出力する。

§10-2 が起票時の予防策であるのに対し、Q5 は実装レーン自身による着手直前の最終チェック。FSA に書かれていない衝突を実装レーンが検知し、設計AI へ確認を上げる構造。

### 10-4. 「ついでに修正禁止」の例外条項

**例外（同一タスクでの処理を許容する）**:
- リファクタで明らかになった**既存バグ**: 報告のみ、修正は別タスク（原則維持）
- **新機能が既存機能の完全上位互換**である場合: 同一タスクで旧機能撤去を許容
- **データ表現衝突**がある場合: 同一タスクで処理を許容（衝突未解消では実装が成立しないため）

**適用条件**: 例外を主張する際は **衝突の不可避性** または **完全上位互換の根拠** を報告書に明記する。曖昧なまま「ついで」で広げる行為は禁止のまま。

### 10-5. 1 bundle = 1 commit

複数タスク統合バッチは **1 bundle = 1 commit** にまとめる。コミットメッセージは個別タスクを箇条書きで列挙する。

**Why**: bundle 単位で commit することで、ユーザーの commit 操作回数が最小化され、bundle 内のタスク群が論理的に関連していることが履歴上も明示される。タスクごとに別 commit すると履歴が冗長化し bundle の意義が失われる。

### 10-6. `.bak` 不要ルール

**ルール**: Edit 前の `.bak` 取得は **不要**。`*.bak*` が `.gitignore` に整備済みであり、`git restore -- <file>` で巻き戻せるため冗長。

**適用**:
- 新規実装・改修で `.bak` を取得しない
- `.gitignore` に `*.bak*` が含まれることが前提（含まれない場合は先に整備する）
- 例外: ロールバックが頻発する実験的フェーズで明示的に保持したい場合のみ、`*.experimental.bak` 等に名前を変えて目的を明示する

**正本での衝突について（本版は確定しない）**: 正本 §10-6 は「Vol.2-2 r6 の『編集前に必ず .bak を取れ』と直接衝突する」と自ら注記し、OS 環境で運用が分岐するか**要ユーザー判断**として未解決のまま残している。

**この未解決事項を本版で確定することはしない。** 正本が明示的にユーザーの判断に留保した事項を、読み替え版が独断で確定するのは §10-7（越権の自己申告）に反する。本版の立場は次のとおり:

- 本版は **git 管理下かつ `.gitignore` に `*.bak*` が整備済み**であることを前提に、`.bak` 不要を**採用**する
- 前提を満たさない環境では、適用前に `.gitignore` を整備する
- **Vol.2-2 との衝突そのものの解消はユーザー判断待ち**（本版では未解決のまま引き継ぐ）

### 10-7. 越権の自己申告ルール

**ルール**: 設計AI は、与えられたスコープを超える提案・改善を**歓迎される行為として積極的に行ってよい**。ただし権限境界を超える場合は、**実行前に自己申告してユーザーの承認を取る**。

「黙って踏み越える」のでも「萎縮して何もしない」のでもなく、「**やりましょう、ただしここは越権なので承認をください**」と明示するのが誠実な振る舞い。

**適用**:
- スコープ外の改善に気づいたら提案する（萎縮しない）
- 権限境界（Handover 更新 §9 / 不可侵スコープ / ユーザーの最終判断領域）を超えるなら、実行前に明示して判断を仰ぐ
- **根拠を示した上での妥当性評価・断定は「越権」ではない**（線引きは「根拠の有無」と「権限境界」）
