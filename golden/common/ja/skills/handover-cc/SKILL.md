**適用条件: あなた（CC）が設計AI 役として、別の CC（実装レーン）へ指示を発行する時。**

## 2. 投下4点セット（CC 版・最重要）

実装レーン CC へ指示を投下する出力では、以下 4 点を全て揃える。**1 点でも欠けたら投下しない。**

| 点 | 内容 | 形式 |
|----|------|------|
| (a) | **指示MD 本体** — 正位置に Write し、**絶対パス**を提示 | MDファイル（パス提示） |
| (b) | **配置の検証** — 正位置に**存在 + 行数 + SHA256 + 先頭/末尾アンカー + 必須見出し** | 地の文（実測値つき） |
| (c) | **/clear 判断とその妥当性** — 根拠つき | 地の文 |
| (d) | **投下プロンプト** — 実装レーンに貼るテキスト | **区切り線で挟んだ平文**（「ここから貼る／ここまで」の 2 行で挟む・1 通に 1 個・内側に説明を混ぜない。固定形は skill `design-lane-order-and-review-cycle` §2-4。コードブロックは CLI で枠に見えず、maintainerがコピー範囲を目視で切り出すことになる（maintainer 2026-09-24 の指摘・台帳 #66）） |

**形式の区別（正本 §3-0 と同一・重要）**: MD 化するのは **(a) 指示書本体だけ**。**(d) 投下プロンプトは「貼り付け用テキスト」ゆえ区切り線で挟んだ平文で出す**（コードブロックで囲まない。コードブロックは CLI で枠に見えず、maintainerがコピー範囲を目視で切り出すことになる（maintainer 2026-09-24 の指摘・台帳 #66））。

### 2-1. 投下前ゲート（出力末尾に必須）

正本の `[Tn]` 行を CC 版に置換したもの。**状態を一言書けない項目は未確認＝欠落。埋めてから投下する。**

```
▸投下前ゲート
  発行元 : cc:<ccId> @ <cwd> / <ISO8601>  role=design ✅
  投下先 : lane=<投下先の cwd or PJ 名>  role=implementation ✅
  MD化   : 指示書を正位置に Write 済 ✅
  4点 (a) 指示MD 絶対パス提示 ✅
      (b) 配置検証: path / sha256 / lineCount / anchors OK ✅
      (c) /clear 判断: <する/しない> — <根拠> ✅
      (d) 投下プロンプト 提示（区切り線で挟んだ平文）✅
  発注の型: <handover-cc 準拠 / handover-cc 非準拠（報告書: <id>／ユーザーの返事: 「<逐語>」）> ✅
```

**「投下先」を必須にする理由**: 正本 §3-4 の保証は「指示元と実装先が**対になって初めて**追跡が成立する」ことにある。発行元だけを記録しても**対にならず、正本が担保していた追跡は復元されない**。投下先 ccId は投下時点では未発番のことがあるため、**最低限レーン識別子（cwd / PJ 名）を必須**とし、実装レーンの ccId が判明した時点で追記する。

**`ccId: unknown` のときは投下しない。** 発行元が確定できない指示は追跡不能な指示であり、正本 §3-4 の禁止（不明を放置して推測で埋めること）に当たる。

### 2-2. (d) 投下プロンプトの形

```
以降のPATHのファイルの指示に従い、実行してください。"<指示MDの絶対パス>"
```

`/clear` が必要な場合、**区切り線の外**に書く（正本 §4-2 と同一）。区切りの内側に `/clear` を混ぜると、そのままコピペした実装レーンが解釈できずエラーになる。

### 2-3. (a)(b) の実行 — CC は移動しない

CC は `Write` で **`{プロジェクトルート}\_Prompt\FromDesignAi\` に直接書く**。DL フォルダを経由しないため、正本 §3-0 (b) の移動コマンドは発生しない。

代わりに **配置の検証**を行う。**存在と行数だけでは不足**（同じ行数の誤ファイル・途中差し替え・古い版の上書き失敗を検出できない）。正本の「作って渡して移動する」一連の物理同一性を、ハッシュで代替する:

```bash
ls -la "<指示MDの絶対パス>" && wc -l "<同>" && sha256sum "<同>" && head -1 "<同>" && tail -1 "<同>"
```

検証すべき 5 点: **path（正位置か） / sha256 / lineCount / 先頭・末尾アンカー / 必須見出しの実在**。

（How は参考。同等以上の同一性が示せれば手段は問わない。§3-3 準拠）

### 2-4. P-Link は不要

P-Link（DL リンク提示機構）は Claude.ai 固有。CC には対応概念が存在しない。**絶対パス提示がその役割を完全に代替する**ため、恒久的に不要。ユーザーに確認する必要もない。

### 2-5. 発注の型の宣言（新設）

投下プロンプトを出す返答の本文に、その発注が本 skill（handover-cc）に準拠しているかを 1 行で宣言する。**宣言の相手はユーザーであって、実装レーンではない**（実装レーンは「handover-cc に従っているか」を知る必要が無い。指示MD には従来どおり What/Why・受け入れ条件・（指定するなら）How を書くだけでよい）。

**準拠するとき**: 投下プロンプトを出す返答の本文に次の行を書く。

```
発注の型: handover-cc 準拠
```

**準拠しないとき（一部外す・別のやり方をとる）**: 2 段に分ける。

1. **先に報告書で示し、承認を取る。** ユーザー向けの報告書を出し、その **H1 の直下（最初の `##` より前）** に次の判断ブロックを置く。長い本文の途中に理由を埋めない。この返答では投下プロンプトを出さない。CLI の本文にも同じ要旨と報告書の URL を載せる。

   ```
   > [!DECISION]
   > 今回は handover-cc に準拠していません。外す条項: …。理由: …。補い: …。この非準拠で進めてよいか、返事をください（「承認」「まかせます」など言い方は自由）。
   ```

2. **ユーザーの返事を受けてから投下する。** 投下プロンプトを出す返答の本文に次の行を書く。

   ```
   発注の型: handover-cc 非準拠（報告書: <report_id>／ユーザーの返事: 「<返事の逐語>」）
   ```

**承認の言い方は問わない。問うのは「人間が返事をした」という一歩があったこと。** 「まかせます」のように、理由を読まずに包括的に任せる返事も承認として扱う。任せたという行為そのものが明示的な一歩として記録に残ることが大事であり、中身を読んだかは問わない。返事が「だめ」「待って」等の不同意なら投下しない。意味の判定に迷う返事は投下せずに聞き直す。**返事の逐語を宣言行に写すのは、後から「何と答えたのに投下したのか」を突き合わせられるようにするため。**

**外してよい理由の書き方**: 「従うと何が悪くなるか」と「外すと何で補うか」の 2 点を書く。例:

> 外す条項: 受け入れ条件の証跡欄を、コマンド出力の代わりに画面録画で代替する。理由: 対象が GUI 操作でコマンド出力が取れない。補い: 実施した操作の録画を残させ、設計AI が受領時に再生して確認する。

**How を指定するとき（発注の型の宣言とは独立の事項）**: §3-3 の「How は参考」の原則から外れて特定の手順どおりに実行させたい場合は、その旨と範囲を指示MD に明記する。**指定した範囲の決定権と責任は設計AI に移る**。これは準拠／非準拠のどちらの発注でも単独で使ってよく、**How を指定すること自体は非準拠を意味しない**（§3-3 の例外条項の範囲内）。実装レーンの規律（impl-lane-plan-review-delivery-cycle）は「指示MD の How は参考、決定権は自分」と定めているため、指定を書かずに How だけ載せると実装レーンはそれを参考として扱ってしまう——指定するなら必ず「これは指定であって参考ではない」と書く。

**推奨の運用は「受け入れ条件の表は外さない」。** ただし外すこと自体は禁じない。外すなら理由を書く。

**機械強制（配備されている環境のみ）**: この宣言は、Stop hook（`handover-declaration-gate`）が配備されている環境では検査される（発注を検出したときのみ）。検査するのは「宣言と形式があるか」「非準拠のときは報告書と人間の返事の逐語が実在するか」までで、証跡欄の中身の正しさや外す理由の妥当性は判定しない（それはユーザーが返事をする前に報告書で見る）。抑制: `~/.ccpit/app-config.json` の `handoverDeclarationGateMode`（soft/strict/off）。

## 3. 指示MD の命名・構造・What/Why/How

### 3-1. 命名規則（正本 §2-2 と同一・器差分なし）

```
{PrjName}_{Step表記}_{通し番号3桁}_{説明}.md
```

保存先: `{プロジェクトルート}\_Prompt\FromDesignAi\`

- 通し番号は **Step（Gen 含む）内で一意**。プロジェクト横断の通し番号は使わない
- 起票前に同フォルダで自 Step の接頭辞を持つ最新番号を確認し、次を採番する
- **ハイフン = 親子階層**（Step[2][1] → `step2-1`）／**ドット = 小数番号**（Step[2.5] → `step2.5`）／**Gen = 世代**（`step2-1Gen5`）。3 つを混同しない
- 説明部の常用語: `investigate` / `fix` / `check` / `build` / `modify` / `verify` / `result`

### 3-2. 指示MD の構造（正本 §2-3 と同一。「概要」に現在地の文書の段を書く注記だけを足した）

```markdown
# タイトル（何をするか）

## 概要
（案件の現在地の文書（段の番号・状態・次の手を表に持ち、状態が変わるたびに書き換える文書。
skill case-journey-map の型。例: `<案件>_MILESTONES.md`）を案件の正本として決めている場合は、
この指示書が進める段の番号（複数の段にまたがるなら全部）と、その文書のパスを書く。）

## 前指示書からの継続制約
（/clear 後に投下する指示書では必須。前の指示書で定義した仕様のうち、
本指示書の作業で実装レーンが触りうるコードに影響するものを列挙する。
引き継ぐ制約がない場合は「なし」と明記。省略禁止。）

## 対象ファイル

## 作業内容
### 作業1: ○○

## 受け入れ条件

## 完了報告
```

### 3-3. What/Why/How の分離（正本 §2-4 と同一・器差分なし）

**What（何を）と Why（なぜ）を明示し、How（どうやるか）は実装レーンに委ねる。**

How に踏み込む場合は「**参考ですが**」「例えば」と断る。実装レーンはそれを参考例として扱い、実行前に現在の実装を調査して有効性を検証する。**設計AI の参考例をそのまま実行して問題が起きた場合、責任は実装レーン側にある。**

| 区分 | 例 |
|---|---|
| OK（What） | 「起動時にデータを読み込みメモリに保持すること」 |
| OK（Why） | 「コールバックのたびに再計算しないこと（パフォーマンスのため）」 |
| NG（How） | 実装コードの構造まで書く／`Select Case` の中身まで指定する |

**例外**: UI 部品の配置位置など、設計者の意図として具体的に決まっているものは明示する。**受け入れ条件は例外ではない**（§5 参照。受け入れ条件は How ではなく What の一部である）。

**完了報告に「How で判断した内容（採用した方法と理由）」を含めさせる。**

#### 制約を書くときの明示義務

制約には**二種類の根拠があり、併存しうる**。

| 根拠の種別 | 例 | 反証が示された場合 |
|---|---|---|
| **技術的正しさ** | 「この関数は正しいので変更不要」 | その前提と、**それだけに依存する**変更不要判断を修正してよい |
| **権限・目的・スコープ** | 「配布系には触るな」「本件のスコープ外」 | **解除されない。** 安全性の主張ではないため |

**技術的根拠への反証は、独立して成り立つ権限・目的・スコープ制約を解除しない。**
どちらの根拠か区別できない制約は、**解除せず根拠を確認する**。

技術的正しさを根拠に「変更不要」とするときは **根拠 / 検証範囲 / 未確認点** の 3 点を書く。
確かめていないなら「**未検証**」と書く。

**整合の確認**: 制約どうし、および制約と設計判断の整合を確認する。矛盾が見つかったら:

- **技術的前提が反証された場合** — その前提と、それだけに依存する変更不要判断を修正する
- **権限・目的・スコープ制約との矛盾** — その境界内で設計判断を修正するか、
  **制約を変更する権限を持つ主体に判断を求める**（実装レーンが独断で境界を動かさない）

## 4. /clear 判断（4点セット (c)）

**毎回明示する。省略して黙って投下することは禁止。**

| 条件 | /clear |
|---|---|
| 前タスクと入力ファイルが重複する | する |
| 前タスクの結果を検証するタスク（クロスバリデーション） | する |
| 完全に独立したタスク（別ファイル・別処理） | どちらでもいい |
| 前タスクの出力を入力にする連続タスク | しない（コンテキスト引き継ぎが有利） |

**/clear する場合は §3-2 の「前指示書からの継続制約」が必須。** /clear は実装レーンのコンテキストを完全にリセットする。前の指示書で確立した仕様制約は、新しい指示書に明示的に書かない限り伝わらない。**実装レーンを縛るのではなく、設計AI 側が仕様引き継ぎの責任を持つ。**

## 5. 受け入れ条件の設計（2026-09-28 改訂）

**「全ての実装要求はテスタブルであるべき」**

受け入れ条件は **How ではなく What の一部**である。「何ができていれば受け取るか」は「何が欲しいか」を検査できる形に言い換えたものであり、作り方には踏み込まない（外部委託でいえば、発注側は仕様書に「受入検査の項目と方法」を書くが、プログラムの内部構造は書かない。同じ線引きがそのまま使える）。

**設計AI（あなた）の責務**: 指示MD に `## 受け入れ条件` を必ず置き、1 行ごとに次の 4 列を書く。

| 列 | 中身 |
|---|---|
| 条件 | 外から観測できる形だけで書く（画面の表示・コマンドの出力・ファイルの中身・API の応答）。内部の作り（関数名・構造）は書かない。書けば How に踏み込むことになる |
| 判定方法 | 設計AI が決める。走らせるコマンド・行う操作・見る場所 |
| 証跡の形 | 報告に貼るもの。コマンド行と出力をそのまま・パス・ハッシュ・画面写真など |
| 区分 | MUST（今回必須）／SHOULD（次回でもよい） |

- 閾値の数値が設計AI の知識では決められない行は、数値欄に「実装レーンが提案し、設計AI が承認する」と書く。判定方法と証跡の形は設計AI が書く
- 全発注に共通の行を必ず置く: 「実施していない確認・取れなかった値は『未実施（理由）』と書く。証跡欄が空の行、出力の写しでなく要約だけの行は不合格とする」
- 報告書に、実在するファイルの行（成果物のコード・設定・既存のコード）を引用させる発注では、共通の行をもう 1 つ置く: 「報告書で実在するファイルの行を引用するときは、md-render の `include=`（写さずに引く）か `cite=`（手で写して照合する）で書く。`include=` で引けるのは md-render が許可する拡張子のファイルだけ（一覧は md-render の該当の節）で、`json`・`yaml` などの許可されない拡張子のファイルは `cite=` で書く。ただし秘密を含む行・秘密を含むと分かっているファイルは、どちらの書き方でも引用せず、必要な内容は秘密を除いて文で説明する」。判定方法は報告書 MD に `md2html.cjs --verify` を実行すること（終了コード 0 で合格）、証跡の形はその出力の写し。説明のための擬似コードや、実在しないコードの例は対象外（属性を付けずに書く）。理由: 報告書の引用が実物に無い・行番号がずれる誤りは、書き手の自己監査の表では止まらなかった（書き方の詳細は skill `md-render` の「コード引用の実物照合」）
- **受け入れ条件の無い指示書は投下禁止。**

```markdown
## 受け入れ条件
| # | 条件 | 判定方法 | 証跡の形 | 区分 |
|---|---|---|---|---|
| 1 | Telegram の応答が sendMessage まで30秒以下になる | 5回連続で実測しタイムスタンプ差分を取る | journalctl の該当行の抜粋 | MUST |
```

### 5-1. 実装レーンの責務（ケッチンの権利）

- Plan の段階で各行を確かめる。**満たせない・その判定方法では測れない行は、根拠を付けて設計AI へ差し戻してよい（ケッチン）。** 黙って条件を読み替えて合格と書くことは禁止
- 差し戻しを受けた設計AI は、指示MD を改訂して版を上げる（口頭で済ませない）
- 報告では、各行に証跡を貼る
- **ケッチンは説明責任を伴う。** 同じ条件に新しい根拠を示さず繰り返し差し戻す、または代替の測定可能な条件を一切提案しないケッチンは、通常の見解の相違と同様に扱い、ユーザーへ判断を仰ぐ

**受領時**: 設計AI は判定方法を自分で1回走らせ、貼られた証跡と突き合わせる（検分の深さは `implementation-review-depth-budget` に従う）。

### 5-2. 実装完了の定義（受け入れ条件への呼び替えに伴い MUST 限定の文言を追加。それ以外は旧方式から据え置き）

以下の全てを満たした場合のみ「実装完了」とする:
1. 受け入れ条件のうち **MUST 区分**の全項目が**実測値**でパス（「パスしたはず」は不可）。**SHOULD 区分**は次回でもよく、未達なら理由を報告に明記する
2. Before/After の実測値が報告に含まれる
3. 「実害なし」等の主観評価で問題を矮小化しない

**コード変更を伴う場合**（正本 §5-6）: テスト PASS だけでは足りない。**release build 成功 + 配布形態の実行ファイルが最新コードで更新されていること**を受け入れ条件に含める。ユーザーは実行ファイルで実機ドッグフーディングするため。

## 6. 自己識別 — 対称版（CC 版で強化される条項）

正本 §3-4 は「指示元＝Claude.ai 上の設計AI の Prj名+チャット名称」「実装先＝CC固有ID」の**非対称**を前提に、両者が対になって初めて追跡が成立すると書く。

**CC が指示元になると両側が ccId を持つ。これは劣化ではなく追跡強度の向上である。**

戸籍簿: `~/.ccpit/.cc-id/<sessionId>.json`

```json
{"ccId":"a1b2c3d4e5","sessionId":"...","cwd":"C://work//projectA","registeredAt":"2026-01-01T00:00:00Z"}
```

ccId は 16進10桁。**cwd を含む**ため、「どの案件フォルダで動いている CC が発行したか」まで機械可読で辿れる。Claude.ai 上の設計AI の「チャット名称」（人間命名・揺れる・欠落しうる）より強い。

**規範**:

| 項目 | 内容 |
|---|---|
| 付与するもの | 発行元 CC の **ccId** ＋ **cwd** ＋ 発行時刻（ISO8601） |
| 付与する場所 | 指示MD の frontmatter または冒頭 |
| 不明な場合 | **推測・命名しない。** 戸籍簿から引く（下記の段階手順）。段を尽くしても収束しない場合にのみユーザーに確認する |

### 自分の ccId を引く — sessionId を確定させ、台帳を直接引く

**この節の全体は「自分の sessionId を確定する」ことに尽きる。** 台帳のレコードは `~/.ccpit/.cc-id/<sessionId>.json` として **sessionId をファイル名に持つ**。sessionId さえ確定すれば、台帳は検索せず**直接 1 件読む**だけで済み、**台帳の横断検索も候補件数の判定も要らない**（読んだレコード自体の整合検査は段 3 で行う）。

**使ってはならない方法**:

- **「最新 1 件」で代用すること。** 台帳はグローバルで数百件あり、並行レーンが走っていれば**別 CC のレコードを掴む**。誤った発行元を正規スタンプとして固定する事故になり、追跡を強化するどころか破壊する
- **`registeredAt` の降順で代用すること。** 降順の上位は「後から登録されたセッション」であって「自分」ではない。並行レーンがあれば他人が上位に来る。登録時刻は現在の実行主体との対応を証明しない性質のものであり、時刻精度を上げても解決しない（秒まで同値の衝突も現に起きる）
- **cwd 一致が 1 件だからといって採用すること。** SessionStart の登録は多くの経路で fail-safe に終了しうる。自分の登録が失敗していれば、cwd に一致する唯一のレコードは**過去の別セッションのもの**である。**件数が 1 であることは本人性の証明ではない**

**段 1 — 記録ディレクトリの特定**

Claude Code は稼働中セッションの発話を `~/.claude/projects/<cwd をマングルした名前>/<sessionId>.jsonl` に追記する（マングル ＝ パス区切りと特殊文字を `-` に置換）。**ファイル名が sessionId である。** 現在の作業ディレクトリから当該ディレクトリを特定する。台帳の cwd 照合は探索範囲の目安にはなるが、**採用根拠にはしない**。

**段 2 — 能動マーカーで sessionId を確定する（唯一の採用根拠）**

使い捨ての一意トークンを 1 つ生成し、**自分のツール実行の引数に載る形で**実行する。段 1 のディレクトリ配下の jsonl を横断し、マーカーを含む行を **JSON として解析**する。

**この手順の信頼の根は、マーカーが「自分だけが知る新規の文字列」であることに尽きる。** 実行系が付与する識別子（`requestId` / `uuid` / `parentUuid`）は、撃つ時点でこちらが知らないため独立な照合子には使えない。以下の条件は本人性の**証明ではなく、誤同定の経路を限定するための整合検査**である。証明でないことを承知の上で採用する。

記録の各行は `sessionId` フィールドを持ち、その値はファイル名（拡張子を除く）と一致する。自分の実行は `assistant` 型の `tool_use` として記録され、他セッションが自分の記録を読んだ場合は相手側の `tool_result` に載る。**この型の差は「自分の実行かどうか」ではなく「その行が実行の記録か引用の記録か」を分けるにすぎない**（他セッションの実行も `assistant` 型になる）。本人性を担うのはあくまでマーカーの新規性であり、型と初出は、マーカーが伝播した後の混入を落とすための条件である。位置（末尾側か）や時刻の近さは代理指標にすぎないので使わない。

**候補**とするのは次を全て満たす行だけ:

1. `type` が `assistant`
2. `message.content[]` に `tool_use` ブロックがあり、その `input` にマーカーを含む
3. その行の `sessionId` が、行を含むファイル名と一致する

**採用条件**（両方を満たしたときだけ）:

- 候補が宣言する `sessionId` の**異なり数がちょうど 1**（生のヒット行数ではない。同一実行が引数と結果の両方に残るため行数は容易に 2 以上になる）
- **かつ**、その sessionId のファイル内でマーカーが**最初に出現する行が候補である**

第二条件は、**逐語的な伝播に限って**引用起点を落とす。他セッションが自分の記録を読めば、その内容は相手の `tool_result` に載る。相手がさらにその文字列でコマンドを撃っても、**読んだ後**の実行である以上、相手のファイル内での初出は `tool_result` になり条件を満たさない。

**この条件が効かない経路（残余リスク）**: 他レーンがマーカーを分割・エンコードされた形で受け取り、復元してから自分の実行に載せた場合、完全な文字列としての初出は相手側の候補になりうる。敵対的でなくとも、正当な調査や再実行の過程でこれは起こりうる。**本手順はこの経路を想定せず、その場合は誤同定しうる**ことを残余リスクとして受け入れる。許容できない用途では、この手順ではなく起動時注入（後述）を待つこと。

**次のいずれかなら採用しない**（段 3 の停止分岐へ）:

- 候補の `sessionId` 異なり数が 2 以上
- 候補が 0 件（後述の再試行後も）
- 初出が候補でない
- マーカーを含む行が JSON として解析できない
- **マーカーを含む行に識別情報の不整合がある**（`sessionId` が欠落している、ファイル名と一致しない）。この場合、その行を候補から外して別の正常な候補を採ることは**しない**。記録の整合性が崩れている以上、他の候補も信用できないため停止する
- いずれかの jsonl が読み取れず、候補判定の網羅性が保証できない
- 2 回の走査で候補集合またはファイル一覧が一致しない

**走査の整合性**: 逐次走査には、読み終えたファイルへの追記や走査中の新規ファイル作成を見落とす余地がある。**走査は 2 回行い、1 回目と 2 回目で候補集合（`sessionId` の集合）が一致することを条件とする。** 一致しない場合、または 2 回目でファイル一覧が変化していた場合は採用しない。

**ただしこれは限定的な変化検出であって、網羅性の保証ではない。** 2 回目に読み終えたファイルへその後追記されれば候補集合は一致したままであり、2 回目の一覧取得後に作られたファイルも捕捉できない。`sessionId` 集合の一致は内容の一致でもない。採用時点までの網羅性を本当に要求するなら書き込み側との同期が要るが、本手順はそこまで踏み込まない。**取りこぼしうることを承知の上で、変化が見えた場合に落とすための条件**として置く。

**候補 0 件のときの再試行**: 実測では、**マーカーを載せた実行と同じ呼び出しの中で候補を取得できた**（250ms 間隔で観測し、初回ポール＝実行開始から 54ms で可視。レコードの `timestamp` は観測開始時刻より 0.68 秒前だった）。ただしこれが示すのは**その時点までに読めたこと**だけであり、「コマンド実行前に書き込まれる」ことまでは測っていない。レコードの `timestamp` は書き込み時刻や可視化時刻とは限らない。したがって「0 件は反映待ちではない」とも断定しない。

**0 件は原因を問わず異常として扱う。** 再試行は間を置いて 1 回までとし、なお 0 件なら段 3 で閉じる（この上限は測定値から導いたものではなく、fail-closed の運用上限として置く）。

補足: 検索コマンド自体にマーカー文字列を直接書くと、その実行も候補になる。ただし同一ファイル内なので `sessionId` の異なり数は変わらず、初出も元の実行のままなので判定は壊れない。気になる場合は検索側で文字列を分割連結して撃つ。

マーカーは作業痕跡に留める。指示MD・報告・成果物には残さない。

**段 3 — 台帳を直接引く、または閉じる**

段 2 で sessionId が確定したら `~/.ccpit/.cc-id/<sessionId>.json` を直接読む。**レコードが存在し、`sessionId` フィールドがファイル名と一致し、`ccId` が 16進10桁**であれば、その `ccId` を採用する。

次のいずれかなら `ccId: unknown` とし、**投下しない**。ユーザーに確認する:

- 段 2 の採用条件を満たさなかった（候補 0 件／`sessionId` 異なり数 2 以上／初出が候補でない／解析または読み取りに失敗した）
- 対応するレコードが存在しない（SessionStart 登録が失敗している）
- レコードが壊れている（`ccId` が不正、`sessionId` がファイル名と不一致）
- 記録ディレクトリまたは台帳が読めない

**記録が読めない・登録が無い場合に、探索を続けずただちに閉じるのは正しい。** fail-closed の要件は「手段を尽くしたか」ではなく、**不確実な識別子で投下しないこと**である。逆に、**収束手段が使える状況で段 2 を試さずに人間へ差し戻すことは禁止する**。それは fail-closed ではなく判断の丸投げであり、識別子を導入した目的（追跡の確立と人間の手数の削減）に反する。

**`unknown` のまま投下することは禁止。** 追跡不能な指示を発行することになり、正本 §3-4 の禁止（不明を放置して推測で埋めること）に該当する。

**禁止**: 発行元を省略したまま実装レーンへ指示を投げること。推測で埋めること。**照合せずに「最新」で代用すること。**

### この節が存在する理由と、その解消条件

本節の探索は、**起動時に発番される識別子がセッション自身へ渡されていない**ことの埋め合わせである。SessionStart の登録処理は実行系から `session_id` を受け取っており、登録の時点で sessionId と ccId の対応を知っている。これをセッションのコンテキストへ渡す経路が備われば、段 1・段 2 は丸ごと不要になり、本節は「渡された ccId を使う。無ければ `unknown`」の 2 行に縮む。

その経路の導入は SessionStart フックの改変であり、**本 skill の適用対象（指示発行時の作法）の外**にある。フック設定は他レーンの起動にも影響する共有資産であり、設計レーンが指示発行の途中で書き換える対象ではない。導入はユーザーの承認のもとで別の変更として扱う。

導入された場合、本節は次の形に縮約する。段 1・段 2 は消えるが、**採用条件は消さない**:

- 渡された ccId が、**現在の sessionId に対応して注入されたもの**であること
- `ccId` が 16進10桁であること
- 台帳に対応するレコードが存在し、その `sessionId` が現在の sessionId と一致すること
- **台帳のレコードが持つ `ccId` と、注入された ccId が一致すること**（`sessionId` の一致だけでは、形式上妥当な別の ccId を排除できない）

いずれかを満たさなければ `ccId: unknown` とし、**投下しない**（`unknown` のまま投下しないという規定は縮約後も生きる）。段 1・段 2 を二重の手順として温存はしない。

## 7. Handover 資料の扱い（正本 §9 の読み替え）

**設計AI 役の CC は Handover を直接参照してよい。** 正本 §9 の「実装AIは直接参照できない」は、Claude.ai 上の設計AI が設計役だった時代の記述であり、CC が設計AI 役の場合には当たらない。

### 7-0. 参照可否は「個体」ではなく「現在の役割」で判定する

ccId は**個体**の識別子であって**役割**の識別子ではない。同一の CC が設計役と実装役を行き来する場合、ccId だけでは「今 Handover を読んでよい立場か」を判定できない。

**判定規則**:

| 現在の役割 | Handover 直参照 | 判定根拠 |
|---|---|---|
| `design`（設計役） | **可** | ユーザーの明示指示、または設計レーンとして起動されたこと |
| `implementation`（実装役） | **不可** | 指示MD に書かれた内容だけで実装する（正本 §9 の核心） |
| 不明 | **不可** | 曖昧なまま参照しない。ユーザーに確認する |

- 指示MD の frontmatter に `issuerRole: design` / `receiverRole: implementation` を記す
- **実装役で動いている間は Handover を直参照しない。** 必要な知識は指示MD に埋め込まれているべきであり、埋まっていないなら設計役へ差し戻す
- 実装役から設計役へ移るには、**ユーザーの明示指示**または**設計レーンとしての起動**が要る。自己判断で昇格しない

**ただし §9 の核心は不変**:

- 実装レーンへの指示書に「**Vol.4-5 を参照して実装せよ**」と書くことは**禁止**。該当部分を指示MD に**直接埋め込む**
  - NG: 「Vol.4-5 の Dash/Plotly ガイドラインに従って実装せよ」
  - OK: 「Dash のレイアウトは3カラム構成とする。スライダーの marks は整数のみ表示。Config 保存時は既存キー保持方式（`existing.update()`）を使用すること」
- Handover の更新は**設計AI が直接編集**する。実装レーンへの指示書経由で Handover を更新させる運用は行わない
