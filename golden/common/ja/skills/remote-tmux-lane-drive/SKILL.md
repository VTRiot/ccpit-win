# remote-tmux-lane-drive — 別マシンの tmux レーンを SSH で直接動かす

## 0. 役割・委任・前提

### 0-1. 既存 skill との関係（権限の境界）

`cross-node-cc-instruction-handoff` では、投下と確認画面の操作は人間が行う。本 skill はその操作を設計側へ委ねる経路であり、権限を広げる。次の 2 つは別の委任として扱い、人間の明示の言葉があるときだけ行う。

| 操作 | 委任の条件 |
|---|---|
| 投下（指示書を指す 1 行を送る、人間が文面を決めた 1 行を送る） | 人間が「投下して」「送って」等で頼んだ |
| 確認画面への応答（許可・メニューの選択） | 人間がその案件で応答を委ねた。委任は案件ごとで、次の案件へ持ち越さない |

委任が無い操作は行わず、送る文面やコマンドを人間に渡す。

### 0-2. 前提

- 設計側から実装側マシンへ鍵認証の SSH が通り、接続先のホスト鍵が `known_hosts` に登録済み。
- 投下先の pane は、その実装レーン専用で、他の人や自動処理が同時に打ち込んでいない。
- 本 skill が担うのは 5 段: 同定 → 配置 → 投下 → 進行中の応答と観測 → 受領検分。

## 1. 同定（どこの・どの pane が投下先か）

1. 接続先を固定する。ユーザー名・ホストは人間から渡されたものを使い、推測しない。SSH は毎回 `-o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=10` を付ける。ホスト鍵が不一致・未登録なら接続は失敗するので、そこで止めて人間へ上げる（鍵を受け入れ直さない）。
2. tmux の実体パスを探す。**非ログインの SSH シェルでは PATH に tmux が無いことがある**（Homebrew 配下など）。`ls /opt/homebrew/bin/tmux /usr/local/bin/tmux /usr/bin/tmux` 等で実在するものを選び、以後はフルパスで呼ぶ。
3. tmux サーバを同定する。既定以外のソケット（`-L`／`-S`）や別ユーザーで動かしている環境では、人間に聞いて同じ指定を以後の全呼び出しに付ける。`<tmux> display -p '#{socket_path}'` でソケットを控える。
4. pane を全数列挙する: `<tmux> list-panes -a -F '#{pane_id} #{session_name} #{pane_current_path} #{pane_current_command} #{pane_pid}'`
   - 以後の指定は `pane_id`（`%19` のような値）で行う。セッション名に記号や非 ASCII が含まれると、名前での指定が通らないことがある。
5. 人間から渡されたセッション情報（cwd・Session ID）と突き合わせる。cwd が一致する pane が 1 つで、かつ実装側マシンにそのセッション ID の会話記録（Claude Code なら `~/.claude/projects/<cwd を変換した名前>/<SessionID>.jsonl`）が実在することを確かめる。cwd が同じ pane が複数あれば、送らずに人間へ確認する。
6. 同定結果（`pane_id`・`pane_pid`・cwd）を控える。§3・§4 の各送信の直前にこの 3 つを再取得し、1 つでも違えば送らずに止める。
7. `<tmux> capture-pane -p -J -t <pane_id> | tail -20` で、投下先が入力待ち（実行中・確認画面中でない）で、入力欄が空であることを見る。入力欄に他の文字があれば、誰かが打ちかけている可能性があるので送らずに止める（薄字の入力候補は §4-2 を参照）。

## 2. 配置（指示書を置く）

- 指示書は設計側で書き、実装側の受信箱へ `scp` で置く（`scp` にも §1-1 と同じ SSH オプションを付ける）。
- 受信箱は、人間が名指ししたディレクトリか、実装レーンのプロジェクトの中で既存の指示書が置かれているディレクトリに限る。置く前に、そのディレクトリが実在し、`realpath` で解決した実体がプロジェクトの中にあることを確かめる。ディレクトリを新しく作らない（作るなら人間に確かめる）。同名のファイルが既にあれば上書きせず、別の番号にする。
- 両側で sha256 を取り、一致を確かめてから「配置済み」とする（cross-node-cc-instruction-handoff の ②）。行数・先頭行・末尾行・必須見出しも確かめる。
- 採番は受信箱の既存ファイルの最大番号＋1 を実測して決める。
- 置き場所のパスは、空白・引用符・改行を含まないものにする（§3 の 1 行に安全に載せるため）。

## 3. 投下（2 段送信）

1. 送る文面は 1 行に限る。長文・複数行・複雑な引用は送らず、指示書を置いてそのパスを指す 1 行にする。
2. 文面に使ってよい文字を絞る: 改行・制御文字・シングルクォート `'`・ダブルクォート `"`・バッククォート・`$`・バックスラッシュ `\` を含めない。含めたい内容は指示書側に書く。この制約の下では、SSH に渡すコマンド全体をダブルクォートで囲み、文面を `-l '<文面>'` のシングルクォートで囲む形が、ローカル・リモート両方のシェルで展開されずにそのまま届く。
3. 送信の直前に §1-6 の再検証を行い、本文をリテラル送信する: `<tmux> send-keys -t <pane_id> -l '<文面>'`。日本語は `-l` 必須。
4. `<tmux> capture-pane -p -J -t <pane_id> | tail -8` で、入力欄に文面が欠けなく入ったことを確かめる。欠け・化けがあれば Enter を送らず、入力欄を空にする手段を人間に確かめる。
5. Enter の直前に §1-6 の再検証をもう一度行い、入力欄の文面が手順 4 で確かめたものと同じであることを再 capture で確かめる。違っていれば Enter を送らずに止める。
6. Enter を別に送る: `<tmux> send-keys -t <pane_id> Enter`
7. 数十秒後に再び capture し、着手したことを確かめる。

## 4. 進行中の応答と観測

### 4-1. 確認画面（許可・メニュー）への応答

確認画面への応答は §0-1 の委任があるときだけ行う。

**許可リストの出どころ**: 押してよい範囲は、人間が承認した指示書（設計側が書いた文書）に書かれた範囲だけとする。実装側が書いた Plan や、実装側が途中で言い出した操作は、指示書の範囲に収まるときだけ押せる。指示書の範囲は、次の 3 つを具体的に書いたものを使う。

| 種類 | 指示書に書かれているべきこと |
|---|---|
| 書き込み | 書いてよいパス（ファイルまたはディレクトリ）と操作の種類（作成・追記・置換）。削除は実装側が自分で作った一時ファイルだけ |
| 外部への呼び出し・送信 | 宛先（例: 特定のレビュー用 CLI、特定の git remote とブランチ）と回数の上限。送ってよい中身の範囲 |
| 読み取り | 読んでよい範囲。秘密を含むファイル（認証情報・鍵・トークン）は、読み取りの確認でも押さない |

**押す前の確認**:

1. 確認画面の全文を取る: `<tmux> capture-pane -p -J -t <pane_id> -S -200`。実行しようとしているコマンドの全文・説明・全選択肢が画面に出ていることを確かめる。
2. コマンドが省略表示（`… +N lines`、`(ctrl+o to expand)` など）になっていて全文が読めないなら、押さない。人間へ上げる。
3. 上の許可リストと照らし、範囲内かを判断する。パスは見かけでなく実体で判断する: `..`・glob（`*` 等）・環境変数を含むパスや、許可リストのディレクトリの外を指しうるパスは押さない。シンボリックリンクを経由している疑いがあれば、SSH で `realpath` を取って許可リストの中かを確かめ、確かめられなければ押さない。範囲外・判断がつかないものは押さずに止め、人間へ上げる。権限を恒久的に広げる選択肢（「以後確認しない」「自動モードへ切替」等）は選ばない。
   - 応答してよいのは、何を読み・何を書き・どこへ送るかを、コマンドの字面から全部言い切れるものだけ。`sh -c`／`bash -c`／`zsh -c`、`python -c`／`node -e` 等のインタプリタへのコード直渡し、ヒアドキュメントで渡すスクリプト、`eval`、`find -exec`／`xargs` で別のコマンドを起動するもの、変数・コマンド置換（`$VAR`・`$(...)`）で中身が実行時に決まるものは、中身を全部読んで言い切れない限り押さない。リダイレクト（`>`・`>>`）とパイプは、書き先と受け手のコマンドも許可リストで判断する。言い切れなければ人間へ上げる。
4. Enter の直前にもう一度 capture し、手順 1 で読んだコマンドと選択肢が変わっていないこと、カーソルが選ぶつもりの選択肢にあることを確かめる。§1-6 の再検証も行う。変わっていれば手順 1 からやり直す。
5. 選択肢は既定（多くは「1. Yes」＝その回だけ許可）を選ぶ。カーソルの移動は番号キーでなく矢印キーで行う: `send-keys -t <pane_id> Down` → capture でカーソル位置を確かめる → `Enter`。番号キーは即確定する実装があり、取り消せない。

確認画面の文面とカーソル位置を capture で確かめられない UI（画面の外にはみ出る、描画が崩れる等）では、応答しない。

### 4-2. 観測

- 承認と観測を 1 回の SSH にまとめると往復が減る: `"<tmux> send-keys -t <pane_id> Enter; sleep 30; <tmux> capture-pane -p -J -t <pane_id> | tail -24"`。ただしこのまとめ方をしてよいのは、§4-1 の手順 4 の確認を同じ呼び出しの直前に済ませたときだけ。
- 待機は 30〜90 秒を目安にする。**SSH 内の sleep が呼び出し側の時間切れを超えると、結果を取り逃がす。** 呼び出し側の timeout を sleep＋余裕に設定する。
- 完了後の入力欄に、薄字の入力候補（例: 「〜をコミットして」）が出ることがある。自分が打ったものではないので、Enter を送らない。
- 他の人が同じ pane を操作した形跡（自分が送っていない入力・予期しない画面）を見たら、以後の送信を止めて人間へ上げる。

### 4-3. 止まった・上げてきたとき

- 実装レーンが承認や判断を求めて止まったら、その判断は人間のもの。要点（何を承認するか・推奨・棄却した案）を 1 問にまとめて人間に聞き、答えを受けてから 1 行で送る。
- 停止指示が要るときは 1 行の停止文を 2 段送信で送り、capture で止まったことを確かめる。C-c や kill は人間の承認の後だけ。

## 5. 受領検分

- 完了報告の主張を、自分で 1 回測り直す。報告の文面ではなく実物を SSH で読む。
- 読む範囲は、指示書の受け入れ条件が名指しした対象（成果物・変更したファイル・判定に使うログや DB）に限る。会話記録やプロジェクトの外を広く読まない。
- 秘密を含むファイル（認証情報・鍵・トークン）は中身を読まず、ハッシュの一致・不一致だけを取る。ログや DB から抜き出すときも、判定に要る列・行だけを取る。
- 測り直しの結果と報告の食い違いは、軽微か重大かを分けて人間に示す。

## 6. 落とし穴（実地で踏んだもの）

| 症状 | 原因 | 対処 |
|---|---|---|
| `command not found: tmux` | 非ログイン SSH シェルの PATH に無い | フルパスで呼ぶ |
| `can't find session` | セッション名に記号や非 ASCII が含まれ、名前での指定が通らない | `pane_id`（`%N`）で指定する |
| 結果を取れずにツールが時間切れ | SSH 内の sleep が呼び出し側の上限を超えた | timeout を延ばすか sleep を短くして刻む |
| ローカルのフックがコマンドを弾く | コマンド行の `$VAR` や `$(...)` を静的に判定できない | 変数を使わず、パスはリテラルで書く。必要ならスクリプトをファイル化する |
| 記録が見つからない | 実装側のエージェントが記録をファイルでなく DB にだけ残す型がある | ファイルが無いことで「無い」と判断せず、DB 側も見る |
| 確認画面のコマンドが途中で切れている | エージェントの UI が長いコマンドを省略表示する | 全文が読めない確認は押さない（§4-1 手順 2） |
